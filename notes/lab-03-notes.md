# Review Questions

**1. Step 8 used a subnet and security group from Lab 2, an instance profile from Lab 1, and a key pair and script from Lab 3. For each of the five, say what would have happened had it been wrong or missing, and which failures would have been immediate and which silent.**  
**Answer:** The subnet, security group, instance profile, key pair and user-data script behave very differently when wrong. A subnet ID that does not exist is rejected immediately with InvalidSubnetID.NotFound, but a subnet that exists and is the wrong one (the private subnet) is a silent failure: the instance launches, gets no public address, and has no route to the internet gateway, so it simply cannot be reached. A security group ID that does not exist fails at once with InvalidGroup.NotFound, but omitting the security group is silent, because the instance gets the VPC's default group and every port the application needs stays closed. An instance profile that does not exist is rejected immediately, but leaving it out entirely is silent: the instance runs with no role, and the failure appears much later in Lab 4 as an S3 credentials error. A missing key pair fails immediately with InvalidKeyPair.NotFound, while a different, valid key pair launches silently and only shows up when nobody can log in. A user-data file that does not exist fails at once in the CLI, but a script with a syntax error or a failing package install is the quietest of all: the instance reports running, and the only evidence is in the bootstrap log on the machine, which is why bash -n and the Step 12 round-trip check matter. Immediate failures are cheap; the silent ones are the ones the read-back checks exist to catch.
    
**2. USMSStudentDataReadWrite grants access to a bucket that does not exist. Explain why this is valid rather than broken, what it means for the instance today, and precisely what changes the moment Lab 4 runs create-bucket. Answer in a full paragraph.**  
**Answer:** An IAM policy is a statement about ARNs, not a reference to objects. USMSStudentDataReadWrite says that principals holding it may perform certain S3 actions on arn:aws:s3:::usms-student-data and its objects, and IAM does not check that anything exists at that ARN, so the policy is perfectly valid today. For the instance, the chain instance, profile, role, policy is already in place, but it has no effect yet: there is nothing at that ARN, so any S3 call would fail with a "no such bucket" error rather than an access error (and on Floci no credentials are delivered to the instance at all). The moment Lab 4 runs create-bucket, the ARN names a real resource, and the same, unchanged policy starts to apply. The head-bucket check that fails today will succeed, and the instance's role will be able to list, read and write objects in that bucket without any credentials being stored on the server. Nothing about the policy or the instance changes; only the world the policy points at does.
    
**3. User data runs once, at first boot. A colleague proposes putting the application deployment in user data so that "restarting the instance redeploys it". Explain why that does not work, and describe two approaches that do.**  
**Answer:** User data runs once, at the first boot of an instance, so stopping and starting the instance does not run it again, and a "redeploy by restart" would silently keep running the old version. Two approaches that do work: first, bake the application into a golden AMI and replace instances from a new AMI (through a launch template and Auto Scaling), so a new version means new instances rather than edited ones; second, use a deployment mechanism that runs on demand, such as a CI/CD pipeline with CodeDeploy or Systems Manager Run Command that pulls the new release onto running instances. A third, lighter option is a per-boot script or a systemd service that fetches the latest artifact each time the instance starts.

**4. Compare Step 10's auto-assigned public address with Step 13's Elastic IP on who owns it, when it changes, what it costs, and what happens on stop. Then describe a failover procedure only possible because of the difference.**  
**Answer:** The auto-assigned address is drawn from AWS's pool and tied to the instance's running state: it is released when the instance stops, a different one is assigned on the next start, and it cannot be moved. An Elastic IP is an address the account owns, independent of any instance: it stays the same across stop/start until it is released, it can be associated with a different instance, and it is billed while allocated (the lab quotes about USD 3.60 a month idle, and AWS now charges for public IPv4 addresses generally, so current pricing should be checked). The difference enables a simple failover: if usms-web-01 fails, associate the same Elastic IP with a replacement instance (using re-association), and every DNS record and client pointing at that address keeps working without changing anything. That would be impossible with an auto-assigned address, which would be lost and re-issued.

**5. An EBS volume cannot attach across Availability Zones, but its snapshot can be restored into any AZ in the region. What does that say about where each is stored, and what does it imply for a system that must survive the loss of one AZ?**  
**Answer:** A volume exists inside one Availability Zone, so it can only attach to an instance in that zone, while a snapshot is stored regionally and can be restored into a volume in any AZ. This shows the volume's data is tied to a single zone's infrastructure, whereas the snapshot lives in regional storage that survives the loss of one zone. For a system that must survive the loss of one AZ, the volume alone is not enough: take regular snapshots (for example with Data Lifecycle Manager) and be able to restore them in a surviving AZ, or run instances in two AZs with replication at the application or database level (such as RDS Multi-AZ), so that the data exists independently of any one zone's volume.   
    
**6. Step 14 could not confirm the application was reachable, so it verified six configuration properties instead. Argue that this is or is not an adequate substitute, and name the class of fault it cannot detect.**  
**Answer:** It is adequate as evidence that AWS side of the path is correct, and it is exactly the real-AWS procedure for "I cannot reach my instance", but it is not a substitute for observing the application working. The checks show that routing, the internet gateway, the security group, the network ACL, the public address and the instance state would allow a request to arrive, but they are necessary conditions, not sufficient ones. The class of fault they cannot detect is everything inside the instance: no process listening on port 80 (nginx not installed or crashed, a failed user-data script, the wrong bind address or port), an operating-system firewall, a full disk, or a broken application. On Floci this is the one link nobody can observe, since no OS runs, so the checks prove configuration rather than behaviour.
    
**7. usms-web-01 and usms-db-01 are both t3.micro from the same AMI. List every difference between them, and say whether each is a property of the instance, its subnet, or the VPC.**  
**Answer:** They share the same AMI, instance type (t3.micro), key pair, Availability Zone and VPC, and nothing about the VPC itself (CIDR, DNS settings, local route) differs between them. Instance-level differences: the instance ID, name and tags, private IP address, the security group attached (usms-app-sg versus usms-db-sg), the instance profile (web has one, db has none), user data (web has the bootstrap script, db has none), the Elastic IP and public address (web only), and the extra EBS data volume (web only). Subnet-level differences: the CIDR range of the private IP, whether the subnet auto-assigns a public address, the route table (default route to the internet gateway versus to the NAT gateway), and the network ACL (default versus usms-private-nacl). The security group definitions themselves live at the VPC level, but which one an instance carries is an instance property.
