Comparing this draft against Step 15's actual v2, two things do not match:

1. **`ecs:RegisterTaskDefinition` cannot be scoped to the service ARN.** My draft put it on the same `Resource` as `DescribeServices`/`UpdateService`, which is a service ARN (`.../service/usms-ecs-cluster/usms-enrolment-svc`). `RegisterTaskDefinition` creates a *task definition* resource, which does not exist yet at authorization time and has no ARN to scope against — IAM simply ignores a resource constraint it cannot evaluate, which in practice means a scoped statement for this action either has no effect or is rejected depending on the evaluator, but on real AWS the documented pattern is `Resource: "*"` (Step 15's `ReadAndRegisterTaskDefinitions` statement). I had conflated "the thing I can register a definition for" with "the service the resulting revision gets deployed to" — those are two different resource types.
2. **The `iam:PassedToService` condition value was wrong.** I wrote `ecs.amazonaws.com`, which is the *ECS control-plane* service principal. The role is actually assumed by the *tasks* ECS launches, whose trust policy (Lab 04's `policies/trust-ecs-tasks.json`) names `ecs-tasks.amazonaws.com`. `ecs.amazonaws.com` never matches that trust relationship, so a condition written against it silently never succeeds — `RegisterTaskDefinition` would be refused with an `iam:PassRole` error that gives no hint the service-principal string itself is the bug. Step 15 uses `ecs-tasks.amazonaws.com`, the same value Lab 04 already committed in the trust policy.

Everything else in my draft — scoping `DescribeServices`/`UpdateService` to one service ARN, and passing exactly the two ECS roles with a condition rather than an unconditional grant — matched Step 15's intent, even though Step 15 splits it into more, narrower statements (`DeployToTheEnrolmentServiceOnly` without the task-definition actions, plus a separate `ReadAndRegisterTaskDefinitions` on `Resource: "*"`) for auditability.

## Step 16 — "Your turn": input artifact swapped to SourceOutput

If the Deploy action's `inputArtifacts` named `SourceOutput` instead of `BuildOutput`, the Deploy action would unzip the *source* archive (`labs/lab-11-pipeline/app/` as packed by `usms-pack-source.sh`) rather than the build's output. `imagedefinitions.json` is written by the `build` phase into `dist/`, which is published as `BuildOutput` because `buildspec.yml` sets `artifacts.base-directory: dist`. The source archive has no `dist/` at all — it has `src/`, `config/`, `tests/`, `buildspec.yml`, `Dockerfile`, and so on, none of which is `imagedefinitions.json` at the archive root.

So the Deploy action would look for `imagedefinitions.json` at the root of `SourceOutput`, not find it, and fail **in the Deploy stage** — not in Build, where the actual mistake (a wrong `inputArtifacts` name in the pipeline document) was made. This is exactly the trap Section 10's "Deploy stage fails immediately, before doing anything" troubleshooting entry describes: the failure surfaces far from its cause because CodePipeline validates artifact *names* when the pipeline document is accepted, but only checks artifact *contents* when the consuming action actually runs.

## Step 18 — "Your turn": what to do about the bad revision (`usms-enrolment:7` in this run)

This repo's actual revision numbers differ from the lab text's hypothetical 2/3/4/5, because the local build/register cycle above was re-run a few times while diagnosing two real Floci behaviours (a `docker push` idempotency hang, and the pipeline's ECS deploy provider being unavailable). The revision that matters for this exercise is **revision 7**, registered during the Step 18 drill and naming `usms-enrolment:r8`, an image that was never built or pushed. The service has already been rolled back to revision 6 (the real `r7` release, deployed via the Known Issues manual-deploy alternative in Step 17), so the bad revision is inert — nothing is running it, and nothing will start running it on its own, because ECS deployments are taskdef revisions a service is explicitly pointed at, and the service's pointer has already moved. The reasoning below applies to whichever revision number a given run actually produces; what matters is the pattern (an ACTIVE revision naming a never-pushed image), not the specific integer.

**Decision: deregister it**, rather than leave it.

The case for leaving it is that a task definition family is meant to be an append-only log (Section 5 and the lab's own framing of "no undo API"), and deregistering removes a record of what was attempted, including the audit trail connecting pipeline execution, `VERSION=r8`, and the fact that the image build/push never happened for that release. That argument is real but weaker here: `outputs/lab-12-deploy-evidence.txt` and the pipeline execution history already keep that record independently of whether the task definition revision itself still exists, and `aws ecs deregister-task-definition` does not delete the revision's metadata — `describe-task-definition` on a deregistered revision still returns it, just with `status: INACTIVE`. Deregistering costs nothing evidentiary.

The case for deregistering is operational: a revision naming an unpushed image is a live trap. `ecs:ListTaskDefinitions` and `ecs:DescribeTaskDefinition` return ACTIVE revisions by default; anyone scanning "what images does this family reference" six months from now — a security audit, an image-pinning migration, someone writing the CloudFormation lab's comparison template — will see that revision pointing at an image that was never pushed, with no annotation explaining why, unless they happen to cross-reference `outputs/lab-12-deploy-evidence.txt` or this notes file. A revision sitting in `ACTIVE` status that silently cannot run is a worse failure mode than one correctly marked `INACTIVE`.

**How somebody would notice without being told:** run `aws ecs list-task-definitions --family-prefix usms-enrolment --status ACTIVE` and diff the resulting revision numbers against which image URIs `describe-task-definition` reports for each, then cross-check each image URI against `aws ecr describe-images --repository-name usms-enrolment` to confirm it actually exists in the registry. A revision whose image has no matching digest in ECR is exactly the signal that should be checked for in any pre-deployment or audit script — and after deregistering it, that revision would no longer appear in the ACTIVE scan, which is the point.

## Section 14 — Review Questions

**1. The ECS deploy action changes exactly one field of the task definition. Name three realistic changes to a service that therefore cannot travel through this pipeline, and describe how you would deploy each of them instead.**

The deploy action's whole mechanism (Section 5) is: read the service's *current* task definition, replace the `image` field of the named container, register that as a new revision, and update the service to point at it. Anything that is not "which image this container runs" cannot travel through it:

- **A change to the container's CPU/memory reservation** (e.g. raising `usms-enrolment`'s task from 256/1024 to 512/2048 because the enrolment service is memory-constrained under load). This has to be done by hand: describe the current task definition, edit the `cpu`/`memory` fields in the stripped JSON (the same describe-strip-register pattern Step 10 uses), register a new revision, and `update-service --task-definition` to that revision — outside the pipeline, or by changing what the pipeline's *build* phase writes into a template it controls, which this pipeline does not do.
- **A change to environment variables or secrets passed into the container** (e.g. adding a new `LOG_LEVEL` variable, or pointing at a different Secrets Manager ARN). `containerDefinitions[].environment` and `.secrets` are untouched by the deploy action; they'd have to be edited the same describe-strip-register way, as a deliberate task-definition change outside this pipeline's Deploy stage.
- **A change to the log configuration** (e.g. switching the `awslogs-group` or adding a new log driver option) — explicitly called out in Step 17's verification ("Log: awslogs" must survive unchanged). Like the above, this requires a hand-edited revision; the pipeline will faithfully carry forward whatever log configuration the *previous* revision had, indefinitely, even if that configuration is wrong or stale.

In all three cases the realistic fix is the same shape: derive a new revision from the current one with Step 10's describe → strip the eight read-only fields → edit the one field that needs to change → register, then either deploy it by hand with `update-service`, or (better, for a real pipeline) extend the Build phase to generate and register the *whole* task definition from a template under version control, rather than relying on the ECS deploy action's single-field patch.

**2. `ecr:GetAuthorizationToken` must be granted on `Resource: "*"` and `ecs:RegisterTaskDefinition` effectively must be too. Are these the same kind of exception? Argue both sides, then commit to an answer.**

*The case that they are the same kind of exception:* both are registry/control-plane-level API calls that create or authenticate against something with no ARN to scope against at the time of the call. `GetAuthorizationToken` issues a token for pulling/pushing to a *registry*, not a specific repository — ECR's resource model has no "registry ARN" at all, only repository ARNs, so there is structurally nothing narrower to write. `RegisterTaskDefinition` creates a *new* task definition revision, and a resource that does not exist yet cannot appear in a `Resource` clause evaluated before the call completes. In both cases, "must be on `*`" is a statement about IAM's resource model, not about AWS being careless with least privilege.

*The case that they are not the same kind of exception:* `GetAuthorizationToken` is a terminal action — having the token lets you *authenticate*, but what you can then do with it is separately constrained by the registry-level ECR actions (Step 12's `PushAndPullTheEnrolmentImageOnly` statement, scoped to one repository ARN). A stolen/misused authorization token is useless without the matching push/pull permissions, which *are* scoped. `RegisterTaskDefinition`, by contrast, is not terminal — registering a task definition is how you hand `usms-ecs-exec-role` and `usms-ecs-task-role` to ECS (`iam:PassRole`), and a task definition can name *any* image, *any* command, and mount *any* volume the task role's permissions allow it to reach. The blast radius of an unconstrained `RegisterTaskDefinition` is therefore bounded only by what the passed roles can do — which is a much bigger lever than "read a token." Exercise 4 exists specifically to test whether the `PassRole` condition actually closes that gap, and the honest answer (see that exercise) is: partially. It stops the pipeline role from registering a definition that uses roles outside the two named ones, but it does not stop a definition that reuses `usms-ecs-task-role` with a completely different image, command, and entrypoint.

**Committing to an answer: no, they are not the same kind of exception.** `GetAuthorizationToken` on `*` is a clean, structural necessity with a narrow, already-scoped follow-on permission. `ecs:RegisterTaskDefinition` on `*` is a structural necessity too, but one whose safety depends entirely on a *different* statement (`PassRole`) doing real work — and Exercise 4 shows that statement does less work than it looks like it does. Treating the two as interchangeable "well, AWS makes you do this sometimes" cases would miss that one needs no further scrutiny and the other needs a compensating control (or an explicit, written acceptance of the residual risk).

**3. Explain to a sceptical colleague why an image digest is worth the inconvenience over a tag. Then make the strongest case against pinning digests in task definitions — there is a real one.**

*Why a digest is worth it:* a tag (`usms-enrolment:r7`) is a mutable pointer — Step 5 deliberately left this repository `MUTABLE`, and Step 18's whole rollback drill exists because a tag can be re-pointed (or, in that drill, simply never resolve) after a task definition was registered naming it. A digest (`sha256:1c92f0ab...`) is derived from the image's content; it cannot be made to point at different bytes without becoming a different digest. If a task definition names a digest, "which bytes is this service running" is answered by the task definition text itself, with no need to trust that nobody re-pushed the tag in between. That is precisely what Exercise 5's evidence chain is built to demonstrate, and precisely the link that a mutable tag breaks once something is retagged.

*The strongest case against pinning digests in task definitions:* a digest is illegible and un-rebuildable from first principles. `usms-enrolment:r7` tells a human reading the task definition what release is running, and (via the registry) can be rebuilt from the same source tag chain if the image is ever lost; `sha256:1c92f0ab...` tells them nothing without a side-channel (a build log, this lab's `outputs/lab-12-image-digest.txt`, or the registry's own tag-to-digest mapping, which may no longer exist if the tag moved or was deleted) to recover what that digest *was*. More concretely: digest-pinning defeats the entire point of `ecr:lifecycle` policies and automatic patch rebuilds. If `nginx:1.27-alpine` ships a security patch and the base image is rebuilt, a tag-based task definition picks it up on the next deploy; a digest-pinned one does not, ever, until someone notices and manually re-pins — silently freezing the service on a known-vulnerable base image is a worse outcome than the provenance risk digests are meant to solve. The honest position is that tags are right for *deploying* (you want the latest build of a release to flow through) and digests are right for *auditing* (you want to prove after the fact exactly what ran) — which is why this lab records the digest in a side file rather than writing it into the task definition.

**4. Step 18's deployment pointed the service at an image that did not exist, and nothing on this emulator objected. On real AWS the circuit breaker would have caught it. Describe a failure the circuit breaker would not catch, and say what mechanism would.**

The deployment circuit breaker (Section 8's "What the circuit breaker does, and does not do" box, and Section 11's table) only watches whether new tasks *start* and pass their *health check*. It has no visibility into application correctness once a task is healthy. A concrete failure it would not catch: release `r8` pulls fine, the container starts, and `GET /healthz.html` returns `200 ok` (Lab 04's health check is exactly this shallow), but the release shipped with a bug that makes the enrolment form silently drop every third submission, or that serves a stale cached `index.html` with the wrong `__RELEASE__` placeholder never substituted (a template bug, not a startup failure). Every task is `RUNNING` and `HEALTHY` from ECS's point of view; the circuit breaker sees nothing to roll back.

The mechanism that *would* catch this is request-level or business-metric monitoring layered on top of the deployment itself: synthetic canary requests exercising the actual feature (not just the health endpoint), CloudWatch alarms on application-level metrics (error rate, enrolment-submission success rate) wired to a deployment's rollback trigger, or — closer to what blue/green with CodeDeploy offers — an `AfterAllowTestTraffic` hook (Step 19's appspec) that runs a real smoke test against the new task set *before* it receives production traffic, rather than ECS's binary "did the container report healthy" signal.

**5. `update-pipeline`, `put-bucket-notification-configuration`, `update-assume-role-policy` and `put-bucket-policy` are all replace-only. What do these APIs have in common that makes replacement the natural design, and what would a merge-based version of `update-pipeline` have to decide that a replace-based one does not?**

What they share: each configures a single, small, internally-consistent *document* — a pipeline's stage list, a bucket's notification routing, a role's trust policy, a bucket's resource policy — where the fields are not independent key-value pairs but an ordered or interdependent structure whose correctness depends on the whole document being considered together. A pipeline's stage list has an order that encodes the artifact dependency chain (Section 16's `Input` column); a notification configuration's filters and destinations interact; a resource policy's statements can be mutually exclusive (an `Allow` and a `Deny` on overlapping conditions). There is no obviously-correct way to "add one field" to a structure whose validity is a property of the whole, so the API designers chose: you read the whole thing, you write the whole thing back, and the service only has to validate one well-defined shape rather than reason about how a partial patch composes with whatever was already there.

What a merge-based `update-pipeline` would have to decide, that a replace-based one does not: where in the stage order a new or changed stage goes (append? insert at a position? what if the caller specifies a stage name that already exists — merge its actions, or replace that one stage wholesale?); what happens to an existing stage the caller's partial document omits — is omission "leave it alone" or "delete it" (this lab's whole Step 16 danger box exists precisely because omission currently means "delete it" under replace semantics, and a merge API would have to pick a *different*, more surprising default to avoid that); and how to merge an action's `configuration` map field-by-field without silently dropping configuration keys the caller didn't mention but that mattered (exactly the `environment` member Step 13 warns is "replaced as a whole" even under the current, simpler replace-only `update-project`). Every one of those is a design decision with a wrong-by-default failure mode, which is exactly what the current design avoids by making the caller own the whole document.

**6. This lab created a second IAM policy version twice and had to set each as default. Why is `create-policy-version` not simply `--set-as-default` by default? Describe the workflow that design is protecting.**

If creating a version always made it the default immediately, there would be no way to stage a reviewed, tested policy change before it takes effect for every principal attached to that policy — which, for a customer-managed policy like `USMSCodeBuildBase` or `USMSCodePipelineBase`, could be attached to more than one role. The two-step design (`create-policy-version` followed by a separate, explicit `--set-as-default` or `set-default-policy-version` call) protects a review-then-promote workflow: write the candidate document, create it as a *non-default* version, validate it against a test context or a staging role, have a second person or a CI check review the diff, and only then flip the default — at which point every principal attached to the policy starts evaluating the new version on their very next request, with no propagation delay to reason about. It also protects rollback: because up to five versions can exist (Step 15's five-version ceiling), a bad promotion can be undone by calling `set-default-policy-version` back to the previous version ID, which is only meaningful if "create" and "promote" are separate, reversible steps rather than one atomic, irreversible one. Step 12 and Step 15's own "Verify" blocks — checking `DefaultVersionId` explicitly rather than assuming the just-created version is active — exist because this two-step design makes "I created it but forgot to promote it" a real, silent failure mode worth checking for every time.

**7. You have `outputs/lab-12-deploy-evidence.txt`, `outputs/lab-12-image-digest.txt`, and the pipeline execution history. A colleague claims the enrolment service is running code that was never reviewed. Which of those three artefacts helps, which does not, and what would you have needed to record at build time to settle it in one command?**

- `outputs/lab-12-deploy-evidence.txt` helps partially: it proves which task definition revision the service was running immediately after a specific pipeline execution, and which image URI that revision names. It is a *deployment* record, not a *provenance* record — it says "this image was deployed," not "this image was built from reviewed source."
- `outputs/lab-12-image-digest.txt` helps partially too: it maps a tag to a digest at a point in time, which answers "did the tag later move" (Exercise 5's whole point), but on its own it does not connect that digest back to a specific commit, pull request, or review — it is evidence about the *image*, not about the *source* the image was built from.
- The pipeline execution history helps the most of the three, but still incompletely: `get-pipeline-execution` and the Source stage's output artifact can show *which S3 object version* (`source/usms-enrolment-src.zip`, a specific `VersionId`) was consumed by a given execution. That is a real link from "this execution" to "this exact zip of source," which is closer to what the colleague is asking about — but it is a link to a *zip in S3*, not to a reviewed commit in a version-controlled repository with a pull-request history, because this pipeline's Source stage is an S3 object (`usms-pack-source.sh` output), not a Git-backed CodeCommit/GitHub source action. None of the three artefacts, individually or together, can show that a *human reviewed* the code before it was packed into that zip, because nothing in this pipeline's Source stage captures review state at all.

What would have had to be recorded at build time to settle it in one command: the build phase would need to stamp the *source control commit SHA* (or, short of using real source control for this lab's zip-based Source stage, at minimum a content hash of the exact source tree) into `build-metadata.json` (which this buildspec already writes, and already includes `sourceVersion` — currently only the *S3 object version*, not a VCS commit, because the Source stage is S3, not CodeCommit/GitHub) alongside whether that commit/SHA had an associated approved pull request. With that in place, one command — reading `build-metadata.json` out of the deployed image, or out of the artifact the Deploy stage consumed — would show the exact commit the running image was built from, and a second lookup against the source-control host's PR API would show whether it was reviewed. Without a real version-controlled Source stage, "was this reviewed" is a question this pipeline's artefacts were never built to answer, and the honest answer to the colleague is that the evidence proves *what is deployed and when*, not *whether anyone looked at it first*.
