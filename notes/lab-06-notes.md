## Step 6 — "Your turn" (MinCapacity 5 while running 2)

**Observed:** `desiredCount` stayed at `2` across the re-registration and for the following few seconds; `describe-scaling-activities` recorded no new entry (`length` stayed `0`).

(a) **Which object made the change — real AWS's documented behaviour, versus what this build did.** On real AWS, raising `MinCapacity` above the current `desiredCount` is the **scalable target's own registration** forcing an immediate correction — no scaling policy or alarm is involved, which is exactly why the lab predicts the count moves "within seconds... with no scaling policy involved". **On this build it did not happen at all**, confirmed separately by Exercise 5's latency measurement (`MinCapacity` raised 2→4, polled for 75 seconds, `desiredCount` never left 2). This is a Floci limitation, not a misunderstanding of which object is responsible.

(b) **The 3 a.m. incident.** The cost of a colleague quietly raising `MinCapacity` to 5 and going to bed: on real AWS, capacity (and its cost) increases immediately and silently — nobody is paged, nothing looks broken, and the service simply runs larger (and more expensively) than intended until someone notices. The single call that would reveal it to the next person on call is `aws application-autoscaling describe-scalable-targets --service-namespace ecs --query 'ScalableTargets[].[ResourceId,MinCapacity,MaxCapacity]'` — comparing the live `MinCapacity` against the value recorded in `configs/lab-06.env` (or any runbook) immediately shows the drift.

**Which one term to change first, and its cost:** the **alarm evaluation term (180s)** is the only one of the four that this lab's own configuration controls directly and the only one where "faster" has no real downside at this traffic pattern — lowering `EvaluationPeriods` from 3 to 1 (matching the custom queue alarm's own choice of 1) cuts 120 seconds immediately. The cost is a noisier, more trigger-happy alarm: a single brief CPU spike (one bad request, one GC pause) would now scale out where three consecutive high periods previously filtered it out as a false positive — trading false-positive resistance for latency. The grace period and task start-up are either someone else's decision (Lab 05, AWS/Fargate) or already as small as the platform allows.

## Observations specific to Floci 2.4.0 (this lab)

- **Managed alarms carry no dead band.** Both the `AlarmHigh` and `AlarmLow` for every target tracking policy report `Threshold: 50.0` (for the CPU policy) — real AWS creates an asymmetric pair (e.g. 50/45) specifically so a metric sitting exactly at target does not oscillate between the two alarm states.
- **Managed alarms do not resolve to the real CloudWatch metric.** `MetricName` is the literal `PredefinedMetricType` string (`ECSServiceAverageCPUUtilization`, `ALBRequestCountPerTarget`) rather than the metric AWS actually publishes under (`CPUUtilization`, `RequestCountPerTarget`), and `Namespace` reads `AWS/ECS` for *both* policies, including the one whose real namespace would be `AWS/ApplicationELB`.
- **A step policy's own `Alarms` field stays empty**, even after `put-metric-alarm --alarm-actions <policy-arn>` creates a real, working link (confirmed functionally in Step 12). Real AWS back-populates this field from any alarm that names the policy; this build does not — a report or audit tool that trusts this field alone will under-report a step policy's alarms (handled in Exercise 3/5 with a reverse ARN lookup instead).
- **`ScaleOutCooldown`/`Cooldown` are stored but not enforced**; `MinCapacity`/`MaxCapacity` **are** enforced once a policy actually computes a new capacity, but **registering a new `MinCapacity` alone does not push `desiredCount`** when no policy evaluates (Step 6's "Your turn", reconfirmed in Exercise 5).
- **The custom metric `USMS/Enrolment EnrolmentQueueDepth` indexed into `list-metrics` on the very first `put-metric-data` call** — no delay, no missing-metric troubleshooting needed.
- **The alarm-evaluation loop runs for real** on a hand-published custom metric with a hand-written alarm, which is the one thing the course's Known Issues page generally does not expect on Floci for this lab.

# Review Questions

**1. Step 15 traced nine lines from a student clicking Register to a task serving the request. Write all nine, name the three this lab owns, and explain why the other six needed no change. Finish with your one-sentence answer to "what does auto scaling change about my application?"**
**Answer:** The nine lines, in order:

1. Requests per target rise past 1000, or the work queue passes 100. *(this lab)*
2. An alarm fires and invokes a policy. *(this lab)*
3. The policy writes `desiredCount`, clamped to 2..10. *(this lab)*
4. ECS starts a task from `usms-enrolment:2`.
5. The task gets an ENI in `usms-private-subnet-a` or `-b`, no public address.
6. `usms-enrolment-sg` admits tcp/80 from `usms-alb-sg` only.
7. The service registers its address in `usms-enrolment-tg`.
8. The load balancer health-checks it; after 60s of grace it takes traffic.
9. Nothing about the task definition, the service, or the load balancer changed.

Lines 4 through 9 needed no change because every one of them was already built and working *before* this lab — the task definition (Lab 04), the private subnets and security group (Lab 02/04), the target group registration and health check (Lab 05) — and Application Auto Scaling's entire job is to write **one number** that those existing, unchanged mechanisms then act on. **What auto scaling changes about my application: nothing about the application itself — it only changes how many copies of the exact same, already-correct application are running at any given moment.**

**2. A colleague passes the service's full ARN to `--resource-id` and gets a validation error. Explain what the resource ID is, why Application Auto Scaling uses a constructed string, and how it differs between the `ecs`, `dynamodb` and `lambda` namespaces. Name the other constructed identifiers this architecture uses and the ARN each comes from.**
**Answer:** The resource ID is **not** the service's ARN — it is a short, human-readable string (`service/<cluster>/<service>`) that happens to be derivable as the *suffix* of the ARN (everything after the last colon: `"${SVC_ARN##*:}"`). Application Auto Scaling uses this constructed form, rather than the full ARN, because the same scaling machinery (scalable targets, target tracking, step scaling, scheduled actions) is shared across nine different AWS services, each with its own ARN shape, and a single short convention per namespace lets one API surface describe all of them uniformly. It differs by namespace because each underlying service names its own resources differently: for `ecs` it is `service/<cluster-name>/<service-name>`; for `dynamodb` it is `table/<table-name>` (or `table/<table-name>/index/<index-name>` for a GSI); for `lambda` it is `function:<function-name>:<alias-or-version>`. Other constructed identifiers this architecture uses, and the ARN each is derived from: the **`ScalableDimension`** itself (`ecs:service:DesiredCount`) is not from an ARN at all but a fixed, namespace-specific enum string; and the **`ResourceLabel`** used by `ALBRequestCountPerTarget` (Step 9) is built from fragments of *two* different ARNs — the load balancer's (`loadbalancer/app/<name>/<id>`) and the target group's (`targetgroup/<name>/<id>`) — concatenated into one six-segment string that exists nowhere as a single AWS-issued identifier.

**3. Registering a target with minimum 2 against a service running one task raises the count to 2 immediately. Which object made that change, and how does it differ from a policy making it? Describe a 3 a.m. incident where someone uses this deliberately, and the evidence left for the person who takes over at 8.**
**Answer:** The change is made by the **scalable target's own registration**, not by any scaling policy — registering a `MinCapacity` above the current `desiredCount` is documented AWS behaviour that corrects the count on the spot, with no alarm, no metric, and no policy evaluation involved at all (confirmed to be absent on this specific Floci build, Step 6's "Your turn"). It differs from a policy making the change in exactly the evidence it leaves: a policy-driven change produces a `describe-scaling-activities` entry whose `Cause` names a specific alarm and policy ("monitor alarm X... triggered policy Y"); a registration-driven change leaves **no such `Cause`** — there is no alarm or policy to name. A 3 a.m. incident where someone uses this deliberately: the enrolment database is struggling under load and an engineer wants more application tasks available *immediately*, without waiting for any alarm to evaluate — they raise `MinCapacity` by hand to force the floor up on the spot. The evidence left for the 8 a.m. handover is **the live `MinCapacity` itself**, now permanently higher than the configured baseline, with **no corresponding scaling activity and no alarm history** to explain why — which is precisely why Review Question 1(b) above flags `describe-scalable-targets` as the one call that reveals this kind of silent, undocumented change.

**4. Target tracking created two alarms; you created a third for the step policy. Compare them: who owns each, what happens when the policy changes or the alarm is deleted, and what one can do that the other cannot. Then argue for breaching as the queue alarm's `TreatMissingData`, and say what would go wrong if you were right.**
**Answer:** The two managed alarms are **owned by Application Auto Scaling**: it names them, creates them as a side effect of `put-scaling-policy`, recreates them if the policy's configuration changes, and deletes them automatically when the policy is deleted (confirmed in Exercise 1/4 — deleting a target tracking policy took its alarms with it, no separate alarm deletion needed). The custom alarm is **owned by the operator** — created separately with `put-metric-alarm`, surviving independently of the policy it happens to point at; deleting the *policy* leaves the alarm behind, pointing at a dead ARN (Exercise 2's clean-up deliberately deletes the alarm first, for exactly this reason), and deleting the *alarm* leaves the policy intact but permanently unreachable by that path. What the operator-owned alarm can do that a managed one cannot: notify **anything** `cloudwatch:PutMetricAlarm` supports as an action — an SNS topic, an Auto Scaling policy, an EC2 action — because it is a general-purpose CloudWatch alarm, not a purpose-built pair; what the managed alarm can do that the custom one cannot (practically) is stay silently, perfectly in sync with its policy's configuration forever, since AWS itself keeps the two consistent.

**For breaching:** I would argue `notBreaching`, not `breaching`, for `usms-enrolment-queue-high` — the metric is **hand-published** in this lab (and, in production, published by the enrolment application itself only while it is actively processing); a gap in data most plausibly means nothing is currently queuing work, which is the *safe* state, not an emergency. **If I were wrong** — i.e., if `breaching` were actually correct here — the failure mode would be the opposite of safe: every time the enrolment service (or whatever publishes the metric) has a transient problem and *stops publishing* this metric, `breaching` would fire the alarm and scale **out**, adding capacity in response to an absence of data rather than a real backlog — exactly the wrong reaction to a monitoring gap, and a standing invitation to runaway cost every time metric publishing itself has a hiccup.

**5. Section 4 says reactive scaling can never absorb the first minutes of a spike. Reconstruct the arithmetic, naming every delay and where it is configured, then explain the three consequences and which of this lab's configuration choices each justifies.**
**Answer:** The arithmetic (worked through in full in Step 8's "Your turn" above): **alarm evaluation** (`Period × EvaluationPeriods`, configured on each alarm — 180s for the managed `AlarmHigh`, 60s for the hand-written queue alarm) + **policy invocation** (≈0s, not configurable) + **task start-up** (not configured by this lab at all; cited as 35.6s locally / 20–60s on real Fargate) + **health-check grace period** (`healthCheckGracePeriodSeconds = 60`, configured in Lab 05, not this lab) ≈ **4–5 minutes** before one additional task becomes useful capacity, and that is only the *first* increment, not a jump straight to the ceiling. The three consequences, and the choice each justifies:

- **"The minimum capacity is a latency decision, not a cost decision."** Justifies the floor of 2 (one task per AZ) existing at all *before* any traffic arrives — it is capacity that costs money every hour specifically so the ~4–5 minute reaction delay above never has to be paid at the start of ordinary operation.
- **"Scale out eagerly, scale in reluctantly."** Justifies the asymmetric cooldowns on every policy in this lab (`ScaleOutCooldown: 60` vs `ScaleInCooldown: 300` on both target tracking policies; `Cooldown: 60` scale-out in Step 10 vs the `300` specified for Exercise 2's scale-in policy) — the ~4–5 minute delay is a cost paid *every time* capacity needs to grow, so growing should never be artificially slowed further, while shrinking (cheap to reverse if wrong) can afford to wait and be sure.
- **"For a spike you know about, use scheduled scaling."** Justifies the two scheduled actions (Step 11) existing as a *third*, non-reactive mechanism specifically for the one case — a predictable morning demand curve — where the ~4–5 minute delay can be eliminated entirely by raising the floor *before* the spike starts, something no alarm-driven policy can ever do by construction.

**6. A CPU policy at 50 and a request policy at 1000 disagree. What happens in each direction, and why is the rule asymmetric? Why are two target tracking policies on the same metric a fault, and why is a step and a target tracking policy on one metric the same mistake?**
**Answer:** When the two policies disagree, **scale-out takes the larger of the two computed capacities** — if CPU's target tracking math says 6 tasks are needed and request count's says 9, the service scales to 9, because under-provisioning is the failure mode scale-out exists to prevent, and taking the smaller number would knowingly leave one signal's demand unmet. **Scale-in only happens when every policy agrees it is safe** — if CPU says 4 tasks would suffice but request count still wants 9, the service stays at 9, because removing capacity that even one signal still needs is the failure mode scale-in exists to avoid. The rule is asymmetric for the same reason cooldowns are asymmetric (Review Question 5): the cost of being wrong is not symmetric between the two directions.

**Two target tracking policies on the same metric are a fault** because each one independently recomputes "the right capacity" from the *same* input using the *same* formula but a *different* target value, so they do not reinforce each other — they produce two different answers for the one question "what should the count be", and the larger-wins/all-agree rule above means the service simply tracks whichever policy's target happens to be currently stricter, making the other one's configuration pure dead weight that misleadingly suggests two independent signals are being watched. **A step policy and a target tracking policy on the same metric are the same mistake in a different shape:** target tracking is continuously *recalculating* a capacity that should make the metric settle at its target; a step policy on that same metric reacts to *crossing a fixed alarm threshold* with a *fixed* adjustment, with no awareness of what target tracking has already decided. The moment the step policy's threshold is crossed, it adds (or removes) a flat number of tasks on top of target tracking's already-converging answer, which immediately moves the metric target tracking is trying to settle, causing it to recompute and move again — the two policies end up correcting each other's corrections rather than cooperating, exactly the "fight to avoid" worked through in Exercise 2.

**7. Give the three reasons `ALBRequestCountPerTarget` beats CPU for the enrolment API, the workload class where CPU is better, and what would have to be true for `ALBRequestCountPerTarget` to scale this service badly, with the metric that would have warned you.**
**Answer:** Three reasons: (1) it measures **demand directly** — requests are the actual thing driving load on a web API, where CPU is only ever an indirect proxy for it; (2) it is **independent of the task's CPU reservation** — this lab's CPU target of 50 is only meaningful relative to the 256-unit reservation in `configs/lab-04.env`, while a request-count target means the same thing regardless of how the task is sized; (3) for an **I/O-bound** API like enrolment, which spends much of its time waiting on `usms-db-01` rather than computing, CPU can stay low even while every task is saturated with waiting requests, so CPU under-reacts precisely when the service is already struggling. **CPU is the better signal for CPU-bound work with a highly variable cost per request** — generating PDFs, transcoding, or image processing, where request *count* alone says little about load but CPU utilization tracks it directly.

**What would have to be true for `ALBRequestCountPerTarget` to scale this service badly:** if requests became **very unequal in cost** — a few expensive operations (submitting an enrolment, a real database transaction) mixed with many trivial ones (health checks, static lookups) — a target value tuned for the *average* request would under-provision exactly when the expensive ones cluster, because the metric cannot distinguish a burst of cheap requests from a burst of expensive ones. The same failure mode occurs if the real bottleneck is **downstream**, specifically `usms-db-01`: if the database saturates first, `ALBRequestCountPerTarget` rising and triggering more tasks only adds more concurrent database connections to an already-overloaded database, making the real problem worse while appearing to "fix" the symptom. **The metric that would have warned me:** `ECSServiceAverageCPUUtilization` staying flat (or `ECSServiceAverageMemoryUtilization`, if memory-bound) while `ALBRequestCountPerTarget` climbs and the service keeps adding tasks — tasks that are, in that scenario, mostly idle, waiting on the same saturated downstream dependency, which is a sign to look at the database's own metrics (connections, CPU, IOPS), not the enrolment service's.
