## Step 3 – Your turn ("EKS is just ECS with different names")

That statement is **false** on the point that matters most for day-to-day operation: ECS with Fargate has almost no data plane for the operator to see at all — AWS runs the instances, patches them, and the right-hand column of Step 3's table is nearly empty — whereas EKS hands the operator real EC2 instances in `usms-eks-nodes` with their own IAM role, their own patching obligation, and their own capacity planning, none of which Lab 04 ever required.

It is **nearly true**, though, once a workload is actually deployed: a Kubernetes Deployment/Service pair and an ECS service/task-definition pair solve the identical problem (N copies of a container, kept alive, reachable by a stable name) with almost a one-to-one mapping of concepts — Step 20's table below makes this explicit — so a colleague who already understands ECS's object model is not starting from zero, only learning a second vocabulary for the same four or five ideas.

## Step 20 – ECS and Kubernetes, compared with both running

| Question | ECS answer | Kubernetes answer |
| --- | --- | --- |
| What holds the container spec? | The task definition (`usms-enrolment:2`), a versioned, immutable JSON document registered with ECS | The Deployment's `spec.template`, a mutable object inside the cluster's own API server |
| What keeps N copies alive? | The ECS service, reconciling `desiredCount` against `runningCount` | The ReplicaSet the Deployment owns, reconciling `replicas` against observed pods — proven directly in this lab when deleting one `usms-enrolment` pod produced a replacement the ReplicaSet created, not the Deployment and not me |
| What gives it a stable name? | The ECS service's registration in `usms-ecs-cluster`, reachable through whatever load balancer Lab 05 attached | The ClusterIP a Kubernetes Service is assigned at creation; it never moves for the Service's lifetime |
| How does another service find it? | Lab 05's target group / ALB DNS name, or service discovery if configured separately | CoreDNS's `<service>.<namespace>.svc.cluster.local` record, built in and proven in Step 16 from inside a pod with no extra configuration |
| What does a rolling update create? | A new ECS deployment inside the same service, with its own `minimumHealthyPercent`/`maximumPercent` | A new ReplicaSet, scaled up while the old one scales down, governed by `maxUnavailable`/`maxSurge` |
| Where does rollback state live? | The previous task definition revision, still registered, reselected by `update-service --task-definition usms-enrolment:1` | The previous ReplicaSet, kept at `replicas: 0` up to `revisionHistoryLimit` (5 here), reselected by `kubectl rollout undo` — demonstrated in Step 18, including the honest gap that rollback reverted the pod template but not the ConfigMap |
| Which IAM role does the app code use? | The task role (`usms-ecs-task-role`), one identity per task definition | On this build, the node role (`usms-eks-node-role`) shared by every pod on the node — Step 21 showed why that is coarse, and that IRSA is the finer-grained real-AWS answer |
| What would I have to change to move to another cloud? | Nearly everything: task definitions, services, target groups and the IAM task role are all AWS-specific constructs | Only the four AWS-side objects (the two IAM roles, the VPC plumbing, the node group); every manifest in `manifests/lab-07/` is byte-identical on any conformant Kubernetes cluster — the portability claim Section 4 makes, now checked against a running system rather than taken on faith |

**Which one would I choose for USMS, and why:** for USMS specifically — a small team, one region, one predictable traffic pattern — I would choose **ECS with Fargate**, because the empty right-hand column of Step 3's control-plane/data-plane table is a genuine operational saving for a team with no dedicated platform engineer, and Lab 04 took noticeably less setup than this lab's 23 steps for an equivalent three-service deployment; I would only reach for EKS if USMS needed something Kubernetes gives that ECS cannot — a HorizontalPodAutoscaler reading a custom metrics pipeline, a service mesh, or genuine multi-cloud portability — none of which is true of USMS today.

## Review Questions (Section 14)

**1. An EKS cluster reports ACTIVE, but every pod sits in Pending. Using the control plane / data plane split from Step 3, explain how both are true, and name two configurations that produce this symptom.**  
**Answer:**
`ACTIVE` is a statement about the **control plane only** — `kube-apiserver`, `etcd` and the schedulers are up and answering, which is everything `describe-cluster` can see, because AWS runs that half and that half alone decides the status field. `Pending` is a **data-plane** fact: the scheduler has accepted a pod but found nowhere to place it, which the control plane's own health has no bearing on at all — the two are reported by entirely different subsystems, exactly the split Step 3 draws. Two configurations that produce this: (a) **no node group at all**, or one whose nodes have not finished joining — an `ACTIVE` cluster with zero `Ready` nodes has nothing to schedule onto; this lab's own Troubleshooting entry 4 names the matching variant, a lone control-plane node that still carries its `NoSchedule` taint, which this build's single node happened not to have (confirmed with `kubectl get nodes -o custom-columns=...TAINTS...`, `<none>`); and (b) **resource requests that exceed every node's allocatable capacity**, demonstrated directly in Step 19's `usms-toobig` pod (`cpu: "64"`, `memory: "256Gi"` against a single small node) — `FailedScheduling` names `Insufficient cpu, Insufficient memory` explicitly, which is a capacity-planning mistake, not a broken cluster.

**2. What would break if you swapped the trust policies of the cluster role and the node role, and at which point in Steps 6 to 11 would you notice on real AWS rather than Floci?**  
**Answer:**
Swapped, `usms-eks-cluster-role` would trust `ec2.amazonaws.com` and `usms-eks-node-role` would trust `eks.amazonaws.com` — neither role could then be assumed by the principal that actually needs it: EC2 instances cannot assume a role that only trusts the EKS service, and the EKS control plane cannot assume a role that only trusts EC2. **On real AWS** the break surfaces immediately and loudly, in Step 8: `create-cluster` calls `sts:AssumeRole` on the cluster role as part of provisioning, and a trust policy naming the wrong principal makes that call fail outright with an access-denied-style error before any control-plane container is even started — the cluster would never leave `CREATING`. **On this Floci build**, by contrast, Section 11's general note that "Floci does not enforce IAM authorization on these calls at all" means `create-cluster` and `create-nodegroup` would very likely both still succeed with the swapped documents attached, because nothing on this build ever actually calls `sts:AssumeRole` against them the way real AWS's control plane does — the mistake would sit undetected, caught only by my own verification script's explicit `Role.AssumeRolePolicyDocument.Statement[0].Principal.Service` checks (which this lab builds exactly because the API alone does not catch it here), or by a careful human reading `get-role` output, not by any failure the API itself would raise.

**3. Take one commonly conflated pair: a Service versus a Deployment, or a readiness probe versus a liveness probe. Explain the distinction and describe a concrete failure caused by getting it backwards.**  
**Answer:**
Readiness controls **membership of the Service** — failing it removes a pod from the endpoint list without touching the container; liveness controls **restarts** — failing it kills and recreates the container, readiness or not. Exercise 3's broken manifest is a clean real example of readiness doing its job correctly: both `usms-broken` pods' containers ran fine (`STATUS Running`), but `kubectl describe` showed `Readiness probe failed: HTTP probe failed with statuscode: 404` on every pod, because the probe pointed at `/healthz` on a stock `nginx:1.27-alpine` image that serves nothing there — the Service correctly had zero endpoints the entire time, and no traffic was ever silently dropped onto a pod that could not serve it. The concrete failure from getting the pair backwards, named directly by Section 13's "Wiring a load-sensitive check to liveness makes a service restart under load": if that same `/healthz`-style check were wired to **liveness** instead of readiness, a pod that is merely slow under a traffic spike — not broken, just busy — would fail the check and be **killed and restarted** by the kubelet, which removes exactly the capacity the spike needed and can cascade: fewer pods take the same load, each one gets slower, more liveness checks fail, more restarts happen. Readiness would have handled the identical slow-pod symptom safely, by pulling the pod out of rotation without destroying it.

**4. After Step 18's rollback, the pod still reported 1.1.0. Explain why, argue for or against "Kubernetes rollback is not really a rollback", and name the practice that resolves the problem.**  
**Answer:**
`kubectl rollout undo` only reverts the **Deployment's pod template** — confirmed directly in this run: the revert moved the pod hash back from `f7f5cc` (revision 3, the restart) to `ff96cc87d` (revision 2, the one with the Secret already wired in), but the response still read `"version":"1.1.0"` because `APP_VERSION` comes from `usms-app-config` via `envFrom`, read live by the container at start, and the ConfigMap is a **separate object the Deployment's revision history never tracked at all** — there was nothing in revision 2 to "roll back to" for that value, because revision 2's ConfigMap reference was always just a name, not a captured value. **I would argue the statement is correct, not an overstatement**: a rollback that silently leaves part of a release's effective configuration in its new state is not a full rollback by any reasonable definition, even though the term is accurate for the one object (the pod template) it actually governs — a reader who assumes "rollback" means "the release is fully undone" will be wrong exactly when it matters, during an incident. The practice that resolves this: **version configuration with the workload** — either embed configuration as an immutable, uniquely-named ConfigMap per release (`usms-app-config-v2`, referenced by the new pod template, so an old revision's template still points at the old ConfigMap name) or manage the whole release, Deployment and ConfigMap together, through a single versioned artifact (a Helm chart, a Kustomize overlay) so one rollback command reverts both — the same principle Lab 06's own notes reach by a different route when a release changes a ConfigMap, a Secret and an image together and only the image comes back on `rollout undo`.

**5. Compare `maxUnavailable: 0` (`usms-enrolment`) with the default (`usms-results`) during an update of two replicas. Give a workload suited to each, and say which is closer to Lab 04's ECS deployment configuration.**  
**Answer:**
With `maxUnavailable: 0, maxSurge: 1`, `usms-enrolment` never drops below its current count of 2 during a roll — a third pod is created and must become Ready before either original pod is touched, so capacity only ever goes 2 → 3 → 2, confirmed by Step 19's `ImagePullBackOff` test leaving both original pods serving untouched while the bad third pod failed on its own. `usms-results`'s default (25%/25% of 2 replicas, rounded to 1 each way) allows one pod to go down **before** its replacement is ready, observed directly in this run's image-tag update: the pod count went 2 → 3 (one new pod added) → 2 (one old pod terminated) rather than holding at 2 throughout, a brief dip in available capacity that `usms-enrolment`'s stricter strategy forbids by construction. **`usms-enrolment`'s `maxUnavailable: 0`** suits a workload where even a momentary capacity drop is costly — a payment API, or exactly an enrolment service during an enrolment period — at the cost of needing headroom for the extra surge pod. **`usms-results`'s default** suits a workload where a brief dip is cheap and the priority is finishing the rollout fast with minimal extra resource use — an internal reporting service, or anything read-only and tolerant of a short gap. **Lab 04's ECS deployment configuration is closer to `usms-enrolment`'s choice**: Lab 04's `minimumHealthyPercent: 100` is exactly the count-based equivalent of `maxUnavailable: 0` (never drop below the current count), which is itself the comparison this lab's own Step 13 annotation already draws.

**6. A colleague says a Kubernetes Secret is "encrypted, so it's fine to commit the manifest". Correct them: what a Secret provides, what it does not, and what you would do on real EKS. Reference Step 17.**  
**Answer:**
They are wrong on the word "encrypted": a Secret's `data` field is **base64**, an encoding, not a cipher — Step 17 demonstrated this directly, decoding `usms-enrolment-secret`'s `ENROLMENT_API_TOKEN` back to `floci-dummy-token-not-a-real-secret` with nothing more than `base64 -d` and no key, no permission beyond `get secret`, and no special tool. What a Secret **does** provide: the value is kept out of the container image, it is a separately RBAC-restricted object (a role can be granted access to Deployments without being granted access to Secrets), and `kubectl describe` hides it from a casual glance at the object — real, useful properties, just not confidentiality at rest. What it does **not** provide: confidentiality of the stored object itself — anyone who can `get` the Secret from the API, or read `etcd`'s data files directly, recovers the plaintext trivially, and (as Step 17 also showed via `printenv` inside the running container) the value is **always plaintext inside the pod**, because that is the only form an application can use it in. Committing the manifest is specifically dangerous because Git never forgets: a base64 string in a commit is a plaintext value in history forever, recoverable long after anyone "removes" it in a later commit — the exact danger Step 17's own callout names. On real EKS I would do three things differently: enable **KMS envelope encryption of Secrets** at the cluster level (closing the `etcd`-at-rest gap this Floci build cannot offer at all, per Section 11), generate Secret manifests only into a git-ignored path (`outputs/`, exactly this lab's own convention) or not generate them as files at all, and prefer a secrets manager plus **IRSA** so the application fetches credentials at runtime rather than having them injected as a stored Kubernetes object in the first place.

**7. For USMS (small team, one region, quiet for eight months and very busy for two), argue for ECS or Kubernetes. Name at least two things this lab made harder than Lab 04 and one thing Kubernetes gave you that ECS could not.**
I argue for **ECS with Fargate**.  
**Answer:**
Two things this lab made harder than Lab 04: first, the sheer step count and surface area — Lab 04 needed one task role, one task definition and one service; this lab needed two IAM roles with two different trust principals, two permissions-policy documents, a dedicated control-plane security group, a cluster, a node group, and only then the three microservices themselves, a materially larger amount to get right before the first container runs. Second, **capacity is now something the team must plan and patch**: Lab 04's Fargate tasks need no instance management at all, while `usms-eks-nodes` are real EC2 instances this lab's own `instanceTypes`/`amiType` fields name but Floci does not provision — on real AWS those are capacity USMS's own small team would have to size, patch and pay for continuously, exactly the operational burden Step 3's control-plane/data-plane table predicts and Lab 04 never imposed. One thing Kubernetes gave that ECS could not, directly observed in this lab: a **portable, declarative application model that needs nothing AWS-specific to describe the application itself** — every manifest in `manifests/lab-07/` would run unchanged on any conformant cluster (confirmed conceptually by Section 4's portability claim and concretely by this lab's Step 16 and Step 18 proofs, none of which referenced an AWS API once the cluster existed), whereas Lab 04's task definitions, services and target groups are ECS-specific documents with no equivalent outside AWS. For USMS's actual shape — quiet most of the year, one sharp seasonal peak — that portability is not worth the year-round cost of the extra control plane and node-patching burden; Lab 06's Application Auto Scaling policies already solve the seasonal-peak problem on top of ECS without requiring a second platform's worth of IAM roles and node group operations.

## Exercise 5 Part 3 – which of the 21 `configs/lab-07.env` variables Lab 08 actually needs

Read against Section 16, in my own words rather than copied from its table:

- `USMS_EKS_CLUSTER` — every single `aws eks` call Lab 08 makes needs the cluster's name, and so does the kubeconfig context switch.
- `USMS_EKS_NODEGROUP` — Lab 08's data-plane scaling step calls `update-nodegroup-config` by this exact name; get it wrong and the wrong node group's bounds change.
- `USMS_EKS_NAMESPACE` — every `kubectl` command Lab 08 runs needs `-n usms` (or the context default this lab already set), so this is the one variable that is really a convenience rather than a strict requirement.
- `USMS_EKS_LB_PORTS` — the one variable the lab calls out as "the one that bites": without the `_lb_ports_` tag already on the cluster, Lab 08's `LoadBalancer` Service has no host port to publish on and Lab 08 Step 15 cannot be completed without recreating the cluster from Step 8 onward.
- `USMS_K8S_DEPLOY_ENROLMENT` — Lab 08 attaches a `HorizontalPodAutoscaler` to this exact Deployment name; it is the one object the HPA's `scaleTargetRef` points at.
- `USMS_K8S_DEPLOY_GATEWAY` — Lab 08 turns this Deployment's Service into first a `NodePort`, then a `LoadBalancer`, so the name has to resolve to the right object across that whole chain.
- `USMS_K8S_CPU_REQUEST` — Lab 08's HPA computes a percentage of this value; knowing it is `50m` lets a reader sanity-check the HPA's target percentage arithmetic by hand instead of trusting the controller blindly.
- `USMS_EKS_ENDPOINT` — after any restart, comparing the live `describe-cluster` endpoint against this recorded value is the one-line check that confirms `kubectl` is still pointed at the right cluster rather than a stale or re-created one (this lab's own Step 22 persistence proof is the direct precedent).

The remaining variables (`USMS_EKS_CLUSTER_ARN/STATUS/VERSION`, both role ARNs, both policy ARNs, `USMS_EKS_CLUSTER_SG`, the three Service names, and `USMS_K8S_MANIFEST_DIR`) are recorded for completeness and for this lab's own verification script, but Section 16's own table does not name any of them as something Lab 08 specifically reads.
