## Review Questions (Section 14)

**1. A colleague proposes moving the whole USMS enrolment API to Lambda@Edge "because it will be faster for everyone". Give the two strongest technical arguments against, and the one situation in which they would be right.**

**Answer:** The first argument is architectural and absolute: a Lambda@Edge function can carry no VPC configuration at all (Section 11's own restrictions table, confirmed directly by Step 14's static checks), so it has no private network path to `usms-db-01` whatsoever — the enrolment API's entire reason for existing is to read and write that database, and an edge function could only reach it by routing through a public endpoint, which defeats the private-networking design every earlier lab in this course built specifically to avoid. The second is operational: an edge function's deployment unit is an immutable, published version, replicated non-transactionally to every point of presence in the price class — real AWS documentation puts this at minutes, not seconds — and the enrolment API, as a business application under active development, needs an iteration and rollback speed Lambda@Edge's replication model is not built to provide; a regional ECS service behind an ALB (what Labs 4–6 already built) redeploys in seconds and the two kinds of workload are not interchangeable on that axis alone. The one situation in which moving to the edge would genuinely be right: if the "enrolment API" in question were reduced to a piece of logic with **no backend dependency at all** — pure request/response transformation, validation, or redirect logic that needs nothing from `usms-db-01` or any other regional service — at which point it stops being "the enrolment API" in any meaningful sense and becomes exactly the kind of stateless, globally-replicated logic Steps 7 and 12 already demonstrate.

**2. Distinguish CloudFront Functions from Lambda@Edge (runtime, trigger points, capabilities, relative cost). Which would you use to add `/index.html` to a URI, to check a JWT signature, and to fetch a per-user redirect from DynamoDB, and why?**

**Answer:** CloudFront Functions run a restricted JavaScript (ECMAScript) subset only, at `viewer-request`/`viewer-response` exclusively, with no network access, no file system, and sub-millisecond execution at a fraction of Lambda@Edge's cost — they are deliberately incapable of anything that is not a pure, synchronous transformation of the request or response in hand. Lambda@Edge runs Node.js or Python, at all four trigger points, with real (if capped) memory and timeout budgets, and — Section 11's restrictions table again — *can* make network calls, though doing so at `viewer-request` means paying that latency on every single request, cache hits included. **Appending `/index.html` to a URI** is a pure string operation with nothing external involved: a CloudFront Function at `viewer-request`, the cheapest and fastest tool for exactly this shape of work. **Checking a JWT signature** depends on what the check actually needs: if it is a symmetric (HMAC) check against a shared secret baked into the function's own code — the same "constants live in the code" discipline Steps 7 and 12 already follow — a CloudFront Function can do it entirely locally, with no network call, and should; if the scheme is asymmetric and requires fetching a JWKS key set from a network endpoint (or checking a revocation list), that network dependency is something CloudFront Functions categorically cannot do, forcing Lambda@Edge regardless of how simple the rest of the check is. **Fetching a per-user redirect from DynamoDB** requires a network call to another AWS service, which only Lambda@Edge can make at all — but making it at `viewer-request` would add real latency to *every* request, including ones that would otherwise be served from cache, so the better placement is `origin-request`, which only fires on a cache miss; this is the same "runs once per miss, not once per request" reasoning Step 12 uses to place the security headers at `origin-response` rather than `viewer-response`.

**3. Step 12 put the security headers at origin-response, not viewer-response, with identical output. Explain the difference in terms of the cache, and describe a requirement that would force viewer-response despite the cost.**

**Answer:** `origin-response` fires once per cache miss — the moment the origin has just answered and before the object is stored — so whatever this function adds becomes part of the cached entry itself and is served, unchanged, to every subsequent request that hits the cache; `viewer-response` fires on every single request, cache hits included, so doing the identical work there would mean recomputing and reattaching the same five headers over and over for objects that never change, at a materially higher invocation count for no different outcome. The two trigger points produce identical output in this specific case only because the headers this function adds depend on nothing about the individual viewer — they are a property of the object, decided once, correctly, at the moment the object enters the cache. A requirement that would force `viewer-response` despite the extra cost is one where the header's value must depend on something that is **not** a property of the cached object and **does** vary per request even for the same cached object — for example, a live, request-time session-validity check that must be able to deny access to an already-cached object for *this specific requester*, something `origin-response` cannot do because it runs only once, at cache-fill time, and bakes one decision in for every subsequent viewer regardless of who they are.

**4. The notifier's execution role grants `s3:GetObject`, and its resource policy lets `s3.amazonaws.com` invoke it. A colleague calls this redundant. Explain who makes which call under each policy, and what breaks if you delete each one separately.**

**Answer:** They are not redundant because they answer two different questions about two different directions of call, exactly as Step 19's own concept block states: the execution role (`usms-lambda-exec-role`, carrying `USMSLambdaBasic`) governs calls the **function itself makes outward** — here, the one call `notifier.py` makes to confirm an object is readable (`s3:GetObject`); the resource policy (the statement `add-permission` attached to `:live`) governs a call made **inward, at the function**, by a completely different principal (`s3.amazonaws.com`, acting as the S3 service on the bucket's own notification configuration) asking to invoke it. Delete the execution role's `s3:GetObject` grant alone, and the trigger keeps firing exactly as before — S3 can still invoke the function, since that permission is controlled entirely by the resource policy — but the handler's own `head_object` call inside the function would fail on real AWS (it is wrapped in `try/except` for precisely this kind of failure, surfacing as `readable: false, read_error: ...` rather than crashing the invocation). Delete the resource-policy statement alone, and the opposite happens: the function's own permissions are untouched and it would still run correctly if invoked directly, but S3 can no longer invoke it through the notification at all — on real AWS, `put-bucket-notification-configuration` actually validates this permission *before* accepting the configuration (Section 10's own troubleshooting entry, `InvalidArgument: Unable to validate the following destination configurations`), so removing the statement after the fact would mean uploads silently stop producing any execution, with nothing in the function's own logs to explain why, since it was never invoked in the first place.

**5. Step 19 added `--source-arn` and `--source-account` to a permission that worked without them. Describe the attack they prevent concretely, name the equivalent mechanism from Lab 09, and say what makes them the same idea.**

**Answer:** Without those two conditions, the resource-policy statement trusts the **service principal** `s3.amazonaws.com` unconditionally — meaning any S3 bucket, in any AWS account, configured by anyone who merely knows this function's ARN (which is not a secret; ARNs are predictable and often logged), could set up a bucket notification targeting `usms-transcript-notifier:live`. Concretely: an unrelated bucket, owned by a different account entirely, could be configured to invoke this function on every upload, consuming this account's Lambda invocation budget and cost for events that have nothing to do with USMS, and handing the handler `bucket`/`key` values describing an object it was never designed to process — exactly the kind of uninvited, cross-account invocation the confused-deputy problem describes. `--source-arn "arn:aws:s3:::usms-student-data" --source-account "000000000000"` closes this by adding `ArnLike`/`StringEquals` conditions that only S3 acting specifically on *this* bucket, in *this* account, can satisfy. The equivalent mechanism from Lab 9 is the identical pair of condition keys — `aws:SourceAccount`/`aws:SourceArn` — added to `usms-ecs-task-role`'s and `usms-transcripts-reader-role`'s **trust policies** in Step 7, to stop *any* ECS task in *any* account from assuming those roles merely because their trust policy named `ecs-tasks.amazonaws.com` unconditionally. What makes them the same idea: both are the fix for an AWS-service principal whose bare name describes the entire service, not one specific instance of it — a condition is the only way to narrow "trusted: this service, generally" down to "trusted: this one resource of that service, specifically," whether the policy being conditioned is an IAM trust policy (who may assume a role) or a Lambda resource policy (who may invoke a function).

**6. Step 14 set environment variables on an edge function and the call succeeded, yet the configuration is invalid. Where does validation actually happen, why is the mistake not rejected immediately, and what does that imply about checking edge configuration? Relate it to the rule that a command appearing to succeed is not evidence it did what you meant.**

**Answer:** Validation happens at a different API call, about a different resource entirely: not `update-function-configuration` (which succeeds correctly, because environment variables are an ordinary, fully legal Lambda feature with no restriction at the function level) but the CloudFront association call — `create-distribution` or `update-distribution` — which checks the function's configuration only at the moment it is actually referenced as a Lambda@Edge trigger, and rejects it there with `InvalidLambdaFunctionAssociation` if environment variables are present. The mistake is not rejected immediately because Lambda itself has no way to know, and no reason to care, that a function configured today might be associated with CloudFront tomorrow — the edge-specific restrictions are a property of *that relationship*, enforced by the service on the other end of it, not a property Lambda polices on every function it stores. The implication for checking edge configuration is that the "point of use" API call cannot be trusted as the place a configuration mistake will be caught early: on real AWS it surfaces, but only much later and against a different resource; on an emulator that does not enforce the association rules at all (this lab's own Floci Limitation note for this step), it may never surface. The only reliable check is a static, independent read of the function's own configuration against the known edge rules, performed *before* any association is attempted — exactly what Step 14's `edge_eligibility()` and the committed `verify-lab-10.sh` both do mechanically. This is a direct instance of the course's own standing rule, stated plainly here: a command's success is evidence only about the one narrow thing that command actually checked — `update-function-configuration` returning cleanly tells you environment variables are now set, and says nothing whatsoever about whether this function remains eligible for the edge role you intend to put it in later.
