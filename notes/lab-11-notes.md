## Step 15's question — an unscoped PassRole Resource with the condition kept

The lab asks what would go wrong if `policies/usms-codepipeline-policy.json`'s `PassTheBuildRoleAndOnlyToCodeBuild` statement kept its `iam:PassedToService: codebuild.amazonaws.com` condition but widened `Resource` from the one role ARN to `"*"`. The condition alone does not save this: it restricts *which service* the passed role may be handed to, not *which role*. With `Resource: "*"`, `usms-codepipeline-role` could pass **any** role in this account to CodeBuild — including, concretely, a role with far broader permissions than `usms-codebuild-role` carries, such as `usms-deploy-role` from Lab 09 (which carries ECS deploy and task-definition permissions) or even an administrative role, if one existed. Anyone able to call `codebuild:CreateProject` or `UpdateProject` with a `serviceRole` of their choosing — not merely the two roles this lab's own IAM policy reviews were written around — could hand that arbitrary role to a CodeBuild project and have a build container assume it, which is exactly how an overly-broad `PassRole` becomes a privilege-escalation path on real AWS. The `Resource` field is the half of the statement that says *which* role may be passed; the condition only narrows *to what service*, and the two are not substitutes for each other.

## Review Questions (Section 14)

**1. A pipeline's Source stage succeeds and its Build stage succeeds, and the deployed application is unchanged. Give two different explanations, one involving `artifacts.base-directory` and one involving the source zip's internal layout, and say how you would distinguish them with one command each.**

**Answer:** The first explanation is that `artifacts.base-directory` does not match where the build actually wrote its output — if the buildspec's `build` phase writes to, say, `dist/` but `artifacts.base-directory` names a different path (or the wrong case, or a typo), `UPLOAD_ARTIFACTS` either uploads an empty artifact or fails to find anything to upload at all, so the Build stage can report `Succeeded` for having *run* without ever producing the files a Deploy stage would need; the deployed application is unchanged because nothing new ever reached it. This is distinguished with one command by listing the uploaded artifact's contents directly: `aws s3api get-object --bucket usms-pipeline-artifacts --key <BuildOutput key> /tmp/check.zip && unzip -l /tmp/check.zip` — if the zip is empty or missing the expected files, this is the cause. The second explanation is that the *source* zip itself has the wrong internal layout — specifically, a top-level directory (for example `app/buildspec.yml` instead of `buildspec.yml` at the root), which this lab's own Step 11 warns about directly. When this happens, CodeBuild typically fails outright with `YAML_FILE_ERROR` rather than silently succeeding, so "Source succeeds, Build succeeds, nothing changes" is a less likely symptom of this cause than of the first — but it remains possible if the buildspec happens to be found at a nested path that still resolves (for example, if `source.buildspec` was itself configured to point one level too deep, consistently). This is distinguished with one command by listing the *source* zip's own contents directly: `unzip -l outputs/usms-enrolment-src.zip` (or `aws s3api get-object` on the uploaded key first) — if `buildspec.yml` and `VERSION` are not at the top level of the listing, this is the cause, independent of anything the artifact-store check would show.

**2. Why does CodePipeline require versioning on an S3 source bucket? Answer in terms of what an execution needs to record about itself, not in terms of "so you can roll back".**

**Answer:** Every pipeline execution must be able to name, permanently and unambiguously, the exact bytes it consumed as its Source stage's input — this is what `get-pipeline-execution`'s `artifactRevisions[0].revisionId` records, and in this lab it is literally an S3 object-version ID (confirmed directly in Step 19: the revision ID returned matched the `VersionId` `put-object` had just returned, character for character). Without versioning, an S3 key is a single mutable slot: a second `put-object` at the same key before or during an execution overwrites the first object entirely, with no way for the execution's own record to distinguish "I read the file as it was at 10:00" from "I read the file as it was at 10:05" — the key alone carries no identity for a specific set of bytes, only for a path. Versioning gives every write at that key a permanent, distinct identifier that an execution's own history can cite forever, even after the key has been overwritten many times since. This is not about rollback (which is a *use* of that record) — it is about the execution being able to state, as a fact about itself and not as an inference, exactly which input it ran against, which is the precondition every later audit, diagnosis, or rollback depends on.

**3. Explain `iam:PassRole` to somebody who thinks it is redundant — "I already have permission to create the project, so why do I need separate permission to say which role it uses?" Their objection is reasonable; answer it.**

**Answer:** The objection conflates two different questions that `iam:PassRole` deliberately keeps separate: "may I create or configure this resource" and "may I hand this *specific* identity to a service for it to act as." Permission to call `codebuild:CreateProject` says nothing at all about which `serviceRole` is acceptable to name in that call — without a separate `iam:PassRole` check, anyone who can create a CodeBuild project could name *any* role in the account as its `serviceRole`, including one far more powerful than anything a build should need, and CodeBuild would then assume that role on their behalf. `iam:PassRole` is the permission that answers the second question independently of the first, and — critically, as Step 15 of this lab builds it — it can be scoped far more narrowly than the resource-creation permission itself: `usms-codepipeline-role`'s policy grants `iam:PassRole` on exactly one role ARN (`usms-codebuild-role`), conditioned by `iam:PassedToService` to exactly one service (`codebuild.amazonaws.com`). The person who can create the pipeline cannot use that same permission to hand it, say, an administrator role to pass to CodeBuild instead — the two permissions bound two independent things, and that is not redundancy, it is exactly the control the objection is missing the point of.

**4. `usms-codebuild-role` and `usms-codepipeline-role` could have been one role with the union of both policies, and the pipeline would work identically. Argue for the two-role design, and then give the strongest argument against it that you can.**

**Answer:** The two-role design means the build container — the piece of this system that executes arbitrary commands from a buildspec a developer wrote, and is therefore the component with the largest practical attack surface — never holds `codebuild:StartBuild`, `codepipeline`'s own artifact-store write permission beyond what the build itself needs, or `iam:PassRole` at all. If a build container were ever compromised through a malicious or careless `buildspec.yml`, the blast radius under the two-role design is exactly `usms-codebuild-role`'s own scope: its log group and the artifact bucket, nothing that could re-invoke CodeBuild, alter the pipeline, or pass any role onward. Under one merged role, that same compromised container would inherit the orchestrator's permissions too — `codebuild:StartBuild`/`StopBuild` on the project, and the `iam:PassRole` grant itself — handing a compromised build the ability to start further builds or manipulate the pipeline's own actions, a materially larger blast radius for the one component least trusted by design. The strongest argument against the two-role design, honestly: it is operationally more to manage for a benefit that, on a small, single-pipeline system like this lab's, is somewhat theoretical — two roles, two policies, two trust documents, and a `PassRole` relationship between them that itself must be reviewed and could itself be mis-scoped (as Exercise 3 found, trivially, for `usms-codebuild-role`'s own trust policy before `aws:SourceArn` was added). For a lab with one build project and one pipeline, a single, carefully-scoped role would be auditable in exactly the same amount of effort and would remove one entire relationship (the `PassRole` statement itself) that could be gotten wrong; the two-role design's real payoff appears once an account has *multiple* pipelines and build projects whose blast radii must stay independent of each other — a scale this lab does not yet reach.

**5. This course's three heredoc forms now appear side by side: `<< 'BUILDSPEC'` in Step 8, `<< META` nested inside it, and `<< EOF` in Step 21. For each, say what would break if it were the other form, and why no error message would tell you.**

**Answer:** `<< 'BUILDSPEC'` (Step 8) is quoted specifically so that `$USMS_RELEASE`, `$ARTIFACT_DIR` and `${CODEBUILD_BUILD_ID:-local}` reach the written file *literally*, as text CodeBuild is meant to expand later, at build time. If it were unquoted (`<< BUILDSPEC`), every one of those variables would be expanded immediately, at the moment the file is *written* on my own machine — `$USMS_RELEASE` and `$ARTIFACT_DIR` are not even set in my interactive shell at that point, so they would simply vanish, leaving `buildspec.yml` with blank values baked in permanently; `${CODEBUILD_BUILD_ID:-local}` would always resolve to `local` even inside a real CodeBuild container, since the substitution already happened before the file was ever uploaded. No error message would appear because this is syntactically completely valid YAML either way — a missing variable just becomes an empty string, not a parse failure, so the buildspec would parse, the build would run, and only a careful read of the *values themselves* (every `$`-prefixed reference silently gone) would reveal the mistake. `<< META` (nested inside Step 8's outer block) is the opposite: it is deliberately *unquoted*, because `build-metadata.json`'s contents are meant to be computed once, at build time, from that build's own `$USMS_RELEASE`/`$BUILT_AT`/`$CODEBUILD_BUILD_ID` values. If it were quoted (`<< 'META'`), the JSON written to `build-metadata.json` would contain the literal strings `$USMS_RELEASE`, `$BUILT_AT`, `${CODEBUILD_BUILD_ID:-local}` and `${CODEBUILD_RESOLVED_SOURCE_VERSION:-local}` verbatim, never substituted — and this, too, produces no error: `json.tool` would parse it as valid JSON (they are just string values), and only `tests/smoke.sh`'s own explicit `grep -q '^ok$'`/placeholder checks (which this file is not covered by) or a human reading the artifact would notice every build reporting the identical, unresolved release string. `<< EOF` in Step 21 is unquoted for the same reason as `META`: every `$(...)` command substitution inside `configs/lab-11.env`'s heredoc must run *now*, while writing the file, so the file on disk contains real, already-resolved values (ARNs, version IDs) rather than shell syntax. If it were quoted (`<< 'EOF'`), `configs/lab-11.env` would be written containing the literal text of every `$(aws ...)` call, never executed — and sourcing that file later would either error loudly (an unresolvable command substitution left as plain text, assigned as a string, is not itself a syntax error in bash) or, worse, silently assign nonsense string values that merely *look* like shell syntax to every downstream variable, which `grep -n 'export .*=$\|None'`'s own check would not catch, since the lines would not be empty — they would just be wrong. In all three cases the common thread is the same: getting quoting backwards produces a file that is still syntactically well-formed, so nothing in the toolchain's own validation (`json.tool`, `bash -n`, `yaml.safe_load`) reports a failure; only reading the actual substituted *content* reveals it.

**6. A colleague proposes removing `pre_build`'s configuration validation because "it duplicates what the deploy stage checks anyway." Under what circumstances are they right? Under what circumstances are they expensively wrong?**

**Answer:** They are right in the narrow sense that, *if* a deploy stage performs an equivalent check and *if* that check runs early enough to prevent any resource consumption or irreversible action before failing, the configuration error will eventually be caught either way — removing `pre_build`'s copy would not let a genuinely broken configuration silently reach production undetected, only move the point of detection later. They are expensively wrong once the cost of *when* a failure is caught is accounted for, which is exactly the trade-off `pre_build`'s own placement in this lab's buildspec is designed around: a `pre_build` failure costs roughly the length of the `install` phase (in this lab's own measured phases, single-digit seconds) and happens before `build` ever runs, before any artifact is produced, and — critically for the real, three-stage version of this pipeline that Lab 12 adds — before a Deploy stage would even be reached, since CodePipeline's stages run in strict order and a failed Build stage never advances to Deploy at all. If the equivalent check lives only in the deploy stage, the same broken `container` value could, depending on exactly where in Lab 12's deploy logic the check sits, survive an entire build (consuming a build minute, uploading a real but unusable artifact) and then fail only once ECS attempts to use `imagedefinitions.json`'s contents, by which point debugging starts from a deploy-time error message that, as Step 20 itself demonstrates, is often far less specific about *which* earlier value was wrong than a `pre_build` check reading the same file directly, with the colleague's own expected container name right there in the code. The decisive circumstance is not "does a check exist somewhere downstream" but "is the cost of failing late, in a context with less specific context about the failure, acceptable" — for a one-word JSON mismatch caught in under ten seconds versus the same mismatch surfacing as an opaque ECS deployment failure some number of minutes later, it is not.

**7. You are asked to prove to an auditor that release `r4` of the enrolment service was built from the source that was in the repository on a particular date. Using only what this lab created, describe the evidence chain you would present, and name the one link in it that is weakest.**

**Answer:** The chain, in order: (1) `labs/lab-11-pipeline/app/VERSION` containing `r4` at the time of the upload, which I can date by (2) the S3 object-version metadata for `source/usms-enrolment-src.zip` — `list-object-versions`' `LastModified` timestamp on the specific `VersionId` that was current when that `VERSION` file read `r4`, which S3 versioning preserves forever even after later uploads supersede it; (3) `get-pipeline-execution`'s `artifactRevisions[0].revisionId` for the specific execution that ran afterward, which I showed in Step 19 matches that exact `VersionId` character for character — proving the pipeline consumed precisely that byte-for-byte source, not some other upload; (4) `list-action-executions`' `externalExecutionId` for that same execution's Build action, a real CodeBuild build ID, establishing that a specific, nameable CodeBuild invocation ran against that revision; and (5), ideally, `build-metadata.json` inside the resulting `BuildOutput` artifact, whose `release` and `sourceVersion` fields would state `r4` and the matching S3 version ID directly, closing the loop from "source as of a date" to "the artifact that resulted." **The weakest link, named honestly, is link (5) on this specific build**: per this lab's own central finding, `usms-enrolment-pipeline/BuildOutput/` never actually received an artifact for any execution this lab ran, so the one piece of evidence that would state the release number *and* the consumed source version together, inside the thing that was actually produced, does not exist here — I can prove the pipeline *started* against exactly the right source (links 1–4 are all genuine, independently-checkable facts), but I cannot, on this account's build, produce the artifact itself as the final, self-describing proof that closes the chain. On real AWS, where the artifact would genuinely exist, link (5) would be the strongest part of the chain rather than the weakest; here, it is the one place where "the pipeline said Succeeded" cannot be upgraded into the artifact-level evidence the rest of this lab's own methodology insists on.
