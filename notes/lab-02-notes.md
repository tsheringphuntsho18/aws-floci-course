# Review Questions

**1. A colleague creates a subnet, names it public-subnet, tags it Tier=public, and turns on auto-assign public IPv4. Instances cannot reach the internet. What is missing, and why did the name, tag and public IP all fail to make it public?**  
**Answer:** The subnet is missing a route table association with a 0.0.0.0/0 -> internet gateway route, so it is using the main route table with no path out. A subnet has no “public” attribute. The name and the Tier=public tag are only labels that nothing in the network reads. Auto-assign public IPv4 only gives instances an address, and that address is useless without a route to the internet gateway. Only routing makes a subnet public.  

**2. Describe a specific USMS request path (ports and direction of each leg) where stateful security groups and stateless NACLs need a different number of rules. Which would you reach for first, and why?**  
**Answer:** Take a student’s browser request: it arrives at the web server on TCP 80, the web server opens TCP 5432 to the database, and the database replies. Security groups need two rules: inbound 80 on usms-app-sg, and inbound 5432 on usms-db-sg sourced from the app group. Replies are allowed automatically because security groups are stateful. NACLs are stateless, so every leg needs its own rule in each direction. The public subnet needs inbound 80, outbound 1024–65535 for the browser reply, outbound 5432, and inbound 1024–65535 for the database reply. The private subnet needs inbound 5432 and outbound 1024–65535. That is about six NACL rules against two group rules. I would reach for security groups first, because they are simpler, stateful, attached per instance, and can reference other groups. NACLs are better kept as a coarse subnet-wide backstop.
    
**3. usms-db-sg allows PostgreSQL from usms-app-sg rather than 10.0.1.0/24. Give two architecture changes that would silently break the CIDR version but not the group-referenced one.**   
**Answer:** Two changes would break the CIDR version silently:

- Scaling the web tier into usms-public-subnet-b (10.0.2.0/24) or any other new subnet. Those instances would fall outside 10.0.1.0/24 and the database would refuse them.
- Putting a load balancer or new compute (ECS tasks, Lambda in the VPC) in front of the database tier, or re-addressing the web tier. The source addresses change, and the rule stops matching.

The group-referenced rule follows membership in usms-app-sg, not addresses, so it keeps working through all of these.

**4. Why must the NAT gateway sit in usms-public-subnet-a? What happens to the private subnet in AZ b if AZ a fails, and what does that say about the real availability boundary?**  
**Answer:** The NAT gateway must be in a public subnet because it needs a route to the internet gateway and a public Elastic IP to translate outbound traffic. In a private subnet it would have no path out. If AZ a fails, usms-nat goes with it. The private subnet in AZ b loses outbound access even though its own instances are healthy. This shows that the real availability boundary is the weakest zonal dependency, not the subnet. A design is only as resilient as its single-AZ components. The fix is one NAT gateway per AZ, each with its own private route table.
    
**5. Describe the path from a private instance to usms-student-data with and without the S3 gateway endpoint. Which path leaves the AWS network, and what does it cost in money and exposure?**  
**Answer:** Without the endpoint, the path is instance, private route table, NAT gateway, internet gateway, then S3’s public endpoint. That path leaves the VPC over public address space. It costs NAT hourly charges plus per-GB processing, and it gives the private subnet an outbound internet path just to reach an AWS service in the same region. With the gateway endpoint, a prefix-list route sends S3 traffic straight to the endpoint. The traffic never touches the NAT or internet gateway, so there are no NAT charges, gateway endpoints are free, and the exposure is smaller. In Floci the route may not appear in the route table, but the endpoint object still exists.
    
**6. Step 23 looked the VPC up by tag instead of reusing VPC_ID. What would not have been proven otherwise? Relate it to Lab 1 Step 14.**  
**Answer:** Reusing VPC_ID would only prove that Bash remembers a string, because a shell variable is unaffected when the container stops. Looking the VPC up by tag goes back to the API and proves the resource itself survived the restart. Checking subnet and security group counts as well catches a VPC that survived empty. This is the same pattern as Lab 1 Step 14: create, perturb, then read the real property back instead of observing a proxy for it.
    
**7. Floci does not enforce security groups. How can you still be confident your Step 14 and 15 rules are correct? Name one mistake this lab's verification catches and one it does not.**  
**Answer:** Floci only stores the rules and does not filter packets, so my confidence comes from reading the configuration back with describe-security-groups. I check that the ports, protocols, and sources are exactly what I intended. For example, usms-db-sg should show SourceSG equal to $APP_SG_ID and SourceCIDR as None. This verification catches a CIDR-based rule instead of a group reference, a wrong port, a missing rule, or an empty or incorrect group ID. It does not catch whether traffic is actually permitted or blocked, because enforcement isn’t tested. It also can’t tell whether the design is right, such as an unintended port or source that is configured exactly as typed, or how the rules interact with the NACL and the groups attached to real instances.
