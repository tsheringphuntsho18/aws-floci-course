## Step 17 Part 2 — the two "what if" sentences on the negative proof

If **control 3** (the private route table's lack of an internet-gateway route) had failed — i.e. if `usms-private-rt` somehow gained an `igw-` route — `usms-db-01` would still be unreachable from the internet because it has no public IPv4 address at all (control 1) and its subnet does not auto-assign one (control 2): there is simply no address for an external packet's reply to resolve to, regardless of what the route table says. If **control 4** had failed — i.e. if `usms-db-sg` admitted a CIDR range instead of only `usms-app-sg` — the instance would still be unreachable from the internet specifically because of controls 1–3: no public address exists to connect *to* in the first place, even though the connection, once initiated from somewhere inside the VPC that could reach it, would no longer be restricted to traffic wearing `usms-app-sg`. Both answers are the same shape as Step 17's own point: each control is independently sufficient against the internet-reachability claim, which is exactly why "five controls" is defence in depth rather than five redundant copies of the same control.

## Exercise 1 — why `usms-bastion-sg`'s egress is different in kind

A workload security group's egress rules describe what the *application* needs to initiate — a fixed, enumerable set of destinations (a database, an object store, a load balancer) that does not change based on who is administering the system. `usms-bastion-sg`'s egress is different in kind because a jump host's entire purpose is to let an *administrator* reach anything in the VPC that legitimate operational work requires, which is not a fixed set known in advance — today it might be SSH to `usms-web-01`, tomorrow a psql session to `usms-db-01` for an emergency query. Its destination should therefore be scoped to the VPC's own CIDR range (`10.0.0.0/16`) on the administrative protocols actually used (SSH, and PostgreSQL if a DBA ever connects through it), not pinned to one application-shaped group the way `usms-alb-sg`'s egress is pinned to `usms-enrolment-sg` — narrowing a bastion's egress to one destination group would defeat the reason a bastion exists.

## Exercise 4 — the security review for the information security officer

### 1. The second front door

`usms-app-sg` still admits `tcp/80` and `tcp/443` from `0.0.0.0/0` directly to `usms-web-01`, unchanged since Lab 02 Step 14 — a second, independent internet-facing entry point that predates `usms-alb-sg` (Lab 05) and was never removed when the load balancer was added. **Should it still be reachable?** No: every production request path this course built after Lab 05 goes through the load balancer, and `usms-web-01` answering directly on the same ports is redundant capacity nobody routes to on purpose — it exists only because removing it was never part of any lab's scope. **What would have to change:** (a) delete `usms-web-01`'s public ingress rules for 80/443 on `usms-app-sg`, keeping only the now-narrowed `tcp/22` rule from `usms-bastion-sg`; (b) if the web tier's application logic still needs to run somewhere, register it as a *target* behind `usms-enrolment-alb` (a new target group, a new listener rule, and — because `usms-app-sg` is not `usms-enrolment-sg` — either a new ingress rule on `usms-app-sg` sourced from `usms-alb-sg`, or moving the workload onto the existing ECS/Fargate path entirely); (c) what breaks: anything that currently reaches `usms-web-01` by its own public IP or DNS name directly, bypassing the ALB, stops working the moment the direct ingress rules are revoked. **The other side, in two sentences:** `usms-web-01` is an EC2-based control-plane convenience Lab 03 built before ECS existed in this course, and keeping a second, narrower entry point (ideally bastion-only) is a legitimate disaster-recovery path if the ALB or the ECS service ever become unavailable at the same time, which argues for *narrowing* rather than fully removing it.

### 2. What egress control actually bought, and what it did not

Three attacker behaviours Steps 13–15 genuinely prevent: (1) a compromised enrolment task opening an arbitrary outbound TCP connection on any port — SSH, SMTP, a raw C2 listener on a non-standard port — since `usms-enrolment-sg`'s egress is now `tcp/443` only; (2) any of the three hardened groups being used to exfiltrate data over DNS, a classic covert channel, since none of them has an open UDP/53 rule to anywhere but the VPC's own resolver (and even that was deliberately left for Exercise 1, not these three groups); (3) a compromised database instance pivoting laterally to another host inside the VPC on an arbitrary port, since `usms-db-sg`'s egress is `tcp/443` only, to `0.0.0.0/0`, not to any other internal address. Two things it explicitly does **not** prevent, and a vendor claiming otherwise should be asked to be specific: (a) an attacker who has already compromised a workload can still exfiltrate the actual data **over the one permitted channel** — `usms-enrolment-sg` and `usms-db-sg` both still permit `tcp/443` to `0.0.0.0/0`, and an HTTPS POST to an attacker-controlled HTTPS endpoint looks identical, at the security-group layer, to a legitimate call to an AWS API; the control (AWS Network Firewall with TLS-SNI/domain filtering, or a forward proxy that whitelists destination hostnames) would close this, at a rough cost of **AWS Network Firewall: ~$0.395/hour per firewall endpoint plus ~$0.065/GB processed** (per the AWS Network Firewall pricing page). (b) Nothing here stops an attacker who is already *inside* one of these three groups' blast radius (an RCE in the enrolment container, say) from reading or writing data the workload's own IAM role already has permission to touch — Steps 13–15 are a network-layer control, and they say nothing at all about what a legitimately-authenticated AWS API call from that compromised workload is allowed to do; that is entirely the IAM side of this same lab (the identity half), at effectively zero marginal infrastructure cost since it is a policy document, not a managed service.

### 4. Detection: what would notice a change, and what to look at first

| Service | Would it catch a security-group rule change, a policy attachment, or an unusual `AssumeRole`? | Preventive or detective? | Free on real AWS? |
|---|---|---|---|
| **AWS CloudTrail** (management events) | Yes — every `AuthorizeSecurityGroupEgress`, `AttachRolePolicy`, `CreatePolicy` and `AssumeRole` call is logged with the calling principal, source IP and timestamp | Detective | Yes — the management-event trail itself is free; cost appears only for data events or extended retention |
| **AWS Config** (rules + configuration history) | Yes — a *rule* like `restricted-ssh` or `iam-policy-no-statements-with-admin-access` evaluates continuously and flags the exact moment a monitored resource drifts out of compliance | Detective (continuous, not just logged) | No — priced per configuration item recorded and per rule evaluation |
| **IAM Access Analyzer** | Partially — it re-evaluates reachability whenever a policy changes, but it answers "is this now reachable from outside," not "did this specific attribute change" | Detective | Yes, for the account/organization analyzer itself |
| **Amazon GuardDuty** | Indirectly — it would flag anomalous *use* of a changed permission (an unusual API call pattern from a credential that just gained new access), not the change itself | Detective | No — priced per event analyzed |
| **CloudTrail + EventBridge rule on `AuthorizeSecurityGroupIngress`/`AttachRolePolicy`** | Yes, in near-real-time, if a rule is written for it — the same CloudTrail data as above, routed to an alert the moment it happens rather than discovered by later review | Detective, but near-real-time | Yes, for the EventBridge rule itself; the receiving action (SNS, Lambda) may cost something |

None of these are **preventive** in the sense of stopping the change — SCPs (Section 11, not modelled here) are the preventive control for "this account can never attach an admin policy," and this course's own permissions boundary (Step 8) is the closest thing to a preventive control actually built here. **What to look at first, in order, the morning after an incident:** (1) CloudTrail, filtered to the suspected time window, for every `Attach*Policy`, `Put*Policy`, `CreatePolicyVersion`, `UpdateAssumeRolePolicy`, `AuthorizeSecurityGroup*` and `AssumeRole` call — this answers *what changed and who changed it* fastest, since it is the raw, unfiltered record; (2) the current output of `usms-iam-audit.sh` and `usms-sg-audit.sh` against the *live* account, diffed against the last known-good run recorded in `outputs/`, to see what the account's posture is *right now* versus what it was; (3) `usms-reachability-matrix.sh`'s "SINGLE POINT OF CONTROL" section, to identify which of the groups the incident touched had no redundant protection to begin with; (4) IAM Access Analyzer's findings for the specific resource involved, to see whether the change actually created new external reachability or only looked alarming in isolation.

## Exercise 5 Part 5 — the two Denies, contrasted in three sentences

`USMSStudentDataReadOnly`'s `Deny` is an **identity-policy** Deny: it stops the specific *roles* that carry this policy (`usms-transcripts-reader-role` today) from ever calling `s3:PutObject`/`s3:DeleteObject`/etc., no matter what resource policy the bucket might later carry, because it is attached directly to the principal and travels with it everywhere. The bucket policy draft's `DenyEveryPrincipalNotOnTheList` is a **resource-policy** Deny: it stops *every* principal in the universe — including ones that do not exist yet, in this account or any other — from touching the bucket unless their ARN is explicitly on the allow-list, which is a fundamentally broader reach than any identity policy can have. The resource-policy Deny is also the only one of the two that applies to a principal in **another AWS account**: an identity policy in this account's `usms-transcripts-reader-role` is never consulted when a principal from account `999999999999` tries to read the bucket, but the bucket's own resource policy — this one — is consulted on every single request to it, regardless of which account the caller is in.

## Review Questions (Section 14)

**1. Step 18 proved five pre-existing verification scripts report exactly what they did before. Explain why that is a strong result, describe a plausible change in this lab that would have broken one of them, and say what you would have done.**

**Answer:** It is a strong result because this lab touched the identity and network **permissions** layer of a system whose verification scripts check the **shape** of that same system — service status, replica/desired counts, listener configuration, security-group *ingress* rules — and a change that altered permissions without altering shape is exactly the outcome a security hardening pass should produce: nothing a legitimate workload does differently, only who/what is allowed to do it and where it may send traffic. Proving this with a diff (`outputs/lab-09-pre-verify.txt` vs. `-post-verify.txt`) is stronger than asserting it, because a diff catches an unintended side effect even when nobody thought to check for it specifically — exactly how Lab 08's Exercise 2 caught its own verify-lab-07.sh regression. A plausible change in *this* lab that would have broken one of the five: if Step 13's authorize-then-revoke on `usms-enrolment-sg` had been done in the wrong order (revoke the allow-all egress *before* authorising the replacement tcp/443 rules), there would have been a window with **no egress at all** on that group; `verify-lab-04.sh` or `verify-lab-05.sh` would not have caught this directly since neither asserts on egress rules, but Lab 06's health-check-dependent checks could plausibly have reported a service as unhealthy if anything in this environment actually carried live traffic through that group during the window. Had a five-script PASS/FAIL count changed, the right response — following Lab 08's own precedent exactly — would be to read the diff first, determine whether the change was a correct, intended consequence of this lab's own work (in which case the earlier script's assertion is now stale and should be updated, as Lab 08 did for `usms-gateway`'s replica count) or a genuine regression (in which case revert the specific change and re-verify), never to simply silence or delete the failing check.

**2. A colleague attaches `USMSPermissionsBoundary` to `usms-deploy-role` with `attach-role-policy`, reasoning it allows the same actions. What changes in that role's effective permissions, in both directions? When would their version become dangerous, and which Section 8 check catches it?**

**Answer:** Nothing changes in the *intersection* either role actually gets to use day-to-day, because `USMSDeployBase` (the identity policy) is already a subset of what `USMSPermissionsBoundary` (the boundary) permits — the effective permission set `identity ∩ boundary` is unchanged either way, since intersecting with a superset changes nothing. What *does* change is the role's structural posture: a boundary attached via `--permissions-boundary` lives in IAM's dedicated boundary slot and can only ever **subtract** from what the identity policy grants, while a boundary attached via `attach-role-policy` becomes an ordinary identity-policy statement that **adds** its own `Allow` grants to the role's effective permissions — in this specific case `USMSPermissionsBoundary`'s own broad `Allow` block (`ec2:Describe*`, `ecs:*`, `elasticloadbalancing:*`, `iam:PassRole`, etc. on `Resource: "*"`) would now itself be a source of granted permissions, not merely a ceiling, which could grant `usms-deploy-role` actions `USMSDeployBase` never intended it to have (everything in that `Allow` statement, not just the narrow deploy-pipeline set). This becomes dangerous the moment someone later tightens `USMSDeployBase` to something narrower, assuming the boundary still caps the role at the old, wider ceiling — but it no longer does, because an ordinarily-attached "boundary" grants exactly as much as it denies, defeating the entire reason a boundary was chosen over a second identity policy. The check that catches the colleague's version is Section 8's **"the boundary is attached to NOTHING as an ordinary policy"** (`verify-lab-09.sh`), which specifically asserts `AttachmentCount == 0` for `USMSPermissionsBoundary` — an `attach-role-policy` call would raise that count to 1 and fail the check immediately, exactly as designed.

**3. Describe a USMS incident in which every ingress rule is correct and the outcome is still a data breach. Which of Steps 13 to 15 would have narrowed it, and by how much? What would have prevented it entirely, and why can this course not build it?**

**Answer:** An attacker compromises the enrolment application itself — a dependency vulnerability in the container image, not a network misconfiguration — and the compromised process, running as a legitimate member of `usms-enrolment-sg` with correctly-scoped ingress (only `tcp/80` from `usms-alb-sg`, exactly as intended), uses the credentials its own task role already legitimately holds to call `s3:GetObject` against every transcript in the bucket and then exfiltrates the data over an outbound HTTPS POST to an attacker-controlled endpoint. Every ingress rule involved is correct throughout; the breach happens entirely through traffic the application was *supposed* to be able to send and receive. **Step 13 narrows it, but only partially:** before Step 13, the same attack could have exfiltrated over *any* port — DNS, a raw TCP socket, SMTP; after Step 13's `tcp/443`-only egress, the attacker is constrained to HTTPS, which is still enough to reach an attacker-controlled server, so the narrowing reduces the attacker's exfiltration channel options from "anything" to "HTTPS to anywhere," not to zero. **What would have prevented it entirely:** a network appliance capable of hostname/TLS-SNI-aware egress filtering — AWS Network Firewall with a domain allow-list, permitting `tcp/443` only to the specific AWS service endpoints and the S3 prefix list the workload legitimately needs, and denying every other HTTPS destination by name. This course cannot build it because Floci carries no actual network traffic for any appliance to inspect (Section 11's governing limitation) — a Network Firewall rule group could be written and attached to the architecture conceptually, but there would be nothing for it to ever evaluate on this platform, making the control impossible to demonstrate rather than merely difficult.

**4. `usms-ecs-task-role` and `usms-transcripts-reader-role` share a trust policy but not permissions; `usms-deploy-role` has a different trust policy and a boundary. For each, what happens if an attacker can call `sts:AssumeRole` for it from their own machine, and why do the answers differ?**

**Answer:** For `usms-ecs-task-role` and `usms-transcripts-reader-role`, an attacker calling `sts:AssumeRole` **directly from their own machine** fails at the trust policy itself, before permissions are ever consulted: both roles' trust conditions require `aws:SourceAccount` to equal this account and `aws:SourceArn` to match `arn:aws:ecs:...:*`, neither of which an external caller's own `sts:AssumeRole` request can satisfy — those condition keys are populated by the ECS service itself when *it* assumes the role on a task's behalf, not by an arbitrary caller, so the confused-deputy fix from Step 7 blocks this specific attack path entirely regardless of which of the two roles is targeted. Where the two then differ is only in what happens *if* that trust check were somehow bypassed (a misconfiguration, not this attack): `usms-ecs-task-role` would hand over full `USMSStudentDataReadWrite` (read and write), while `usms-transcripts-reader-role` would hand over only `USMSStudentDataReadOnly`'s read-only grant with writes explicitly denied — the same trust failure, but a smaller blast radius on the permissions side for the reader role, which is the entire point of Step 7's split. For `usms-deploy-role`, the trust policy names a specific IAM **user** (`usms-admin-01`) as principal rather than a service, so an external attacker's `sts:AssumeRole` call fails for a different reason: the caller is never that user, and nothing about an external machine's identity can satisfy an `AWS` principal condition the way it can (incorrectly) attempt to satisfy a service-principal condition. If this role's trust were somehow bypassed, the permissions boundary caps the damage structurally differently from the other two roles' lack of one: even a successfully-assumed `usms-deploy-role` session is capped to the intersection of `USMSDeployBase` and `USMSPermissionsBoundary`, which denies every identity-changing action outright (`iam:CreateUser`, `iam:AttachRolePolicy`, etc.) — a second, independent ceiling neither `usms-ecs-task-role` nor `usms-transcripts-reader-role` has. The answers differ because the three roles sit on two different axes of this lab's own design: *who* may assume them (service vs. named user, the trust-policy axis) and *how much damage* a successful assumption could do (unscoped vs. scoped permissions, with or without a boundary) — and this question deliberately picks roles that differ on one axis while holding the other constant, to show the two axes are independent.

**5. Why is "five controls" on `usms-db-01` not simply five times better than "one control" on `usms-enrolment-sg`, given the specific failure modes involved? Are the enrolment tasks genuinely less well protected, given what Step 17 says the matrix models?**

**Answer:** "Five controls" and "one control" are not on the same scale because they answer different questions: `usms-db-01`'s five controls (no public IP, no subnet auto-assign, no IGW route, a single-group-sourced security rule, a non-default NACL) are five *independent* mechanisms protecting the *same* claim — "nothing on the internet can reach this host" — so the claim survives any single control's failure, which is what defence in depth actually buys. `usms-enrolment-sg`'s "single point of control" finding from the reachability matrix is a different kind of statement entirely: it means exactly one *ingress rule* governs who may open a connection to anything wearing that group (`tcp/80` from `usms-alb-sg`), not that the enrolment tasks have only one *layer* of protection overall — Step 17 itself says explicitly that the matrix "models security groups only," and the enrolment tasks additionally sit in a private subnet with no public address and no IGW route, identically to the database tier, which the matrix's own security-group-only scope does not surface. So no, the enrolment tasks are not genuinely less protected than the database by some 5-to-1 ratio; they are protected by the same network-placement controls as the database, *plus* one security-group rule that happens to be the only ingress rule on that particular group — a legitimate, narrower finding ("if this one rule is ever misconfigured, nothing else at the security-group layer would catch it") that a reader must not conflate with "this workload is five times weaker," because the tool that produced the "one control" number was never asked the same five-axis question the database's manual proof was.

**6. What does each of the two extra rotation steps in Step 10 protect against, and what incident would each prevent? Why is a long-lived key a compromise, and what would a real system use for a human and for a workload?**

**Answer:** The two extra steps beyond "create a new key and use it" are **deactivate** (step 3) and the gap between deactivate and **delete** (step 4). Deactivating first, rather than deleting immediately, protects against an incomplete rotation: if some consumer of the old key was missed (a script, a second profile, a CI job) and the new key alone does not actually work for every use, a deactivated key can be reactivated in one command with zero data loss, whereas a deleted key is gone permanently and AWS never re-issues the same secret. The incident this prevents: rotating a credential and discovering ten minutes later that an unlisted automation broke, with no way back except generating and redistributing an entirely new key under time pressure. The gap itself — checking `aws sts get-caller-identity --profile usms-dev` *after* deactivation and *before* deletion — protects against exactly that scenario by surfacing the break while it is still cheaply reversible, rather than after the only fallback has been destroyed. A long-lived access key is a compromise because its blast radius is open-ended in time: unlike a session credential that expires in minutes or hours, a static key grants the same access for as long as it exists, with no automatic re-authentication step that would require the credential to be live and healthy — if it leaks once, quietly, it remains valid until a human notices and rotates it, which could be months. A real system would use **IAM Identity Center (SSO) or federation** for a human (temporary, short-lived credentials issued per session, tied to an identity provider's own authentication, and automatically expiring) and an **IAM role with no long-lived credentials at all** for a workload (an EC2 instance profile, an ECS task role, or a Lambda execution role — exactly the pattern every *other* identity in this lab already uses, which is precisely why `usms-dev-01`'s access key is the *one* long-lived credential anywhere in this course, kept only because Lab 02's `assume-role` handshake needs a named human principal to start from).

**7. Argue whether Section 11's review methodology is an adequate substitute for testing. Name a defect reading catches that testing would not, and one testing catches that reading would not. Which would you want first for student transcripts?**

**Answer:** Reading is not an adequate *substitute* for testing, but it is the only adequate method for the specific class of claim this lab makes repeatedly — a negative, "this cannot happen" claim about an environment (Floci) that enforces nothing and therefore cannot be made to fail a test even when the configuration is wrong, as Step 6's own Floci Limitation note states directly: Floci authorises every call regardless of the policy document, so a test that tries `s3:PutObject` under the read-only role would *succeed* on this platform whether or not the policy is actually correct, telling you nothing. A defect **reading** catches that **testing** would not, on a platform like this one: `USMSPermissionsBoundary`'s own `Resource: "*"` on its Allow statement is not flagged by `usms-iam-audit.sh`'s wildcard-resource check (by design, since a ceiling legitimately needs a broad `Resource` to cap a broad identity policy) — only reading the document's *intent* (a boundary, never attached, used only via `--permissions-boundary`) distinguishes "a necessary broad ceiling" from "an over-permissive grant," a distinction no automated test of *behaviour* could draw on Floci, since nothing here ever actually gets denied by anything. A defect **testing** catches that **reading** would not: a typo in a security-group rule's port number, or a Condition block whose key name is subtly wrong (`aws:SourceAccnt` instead of `aws:SourceAccount`, say) — reading the JSON carefully can miss a single-character error that *looks* syntactically plausible, where a genuine behavioural test against a real-AWS evaluator (`simulate-principal-policy`, which this build happens to support) would immediately report `implicitDeny` on an action the author believed was conditioned correctly, exactly as this lab's own Step 9 used it as a second opinion against a hand-read intersection. For student transcripts specifically, I would want **reading first**: the stakes of an incorrectly-reasoned policy reaching production are high and the feedback loop for "did I understand this document correctly" is immediate and free, whereas a behavioural test on real AWS risks being run against production data if anything goes wrong, and in any case the controls that matter most here — an explicit Deny, a trust condition, a boundary's ceiling — are precisely the kind of static, document-level property reading is suited to catch before anything is ever exposed to a test in the first place.
