Worse than expected on the companion claim: the cluster's own `_lb_ports_=8081,8082` tag (written at `create-cluster` time specifically so a `LoadBalancer` Service would have a host port to publish on) **never actually caused Docker to publish 8081 or 8082** — confirmed by the same `docker port` output above and by `curl`ing both ports from the host, both of which failed. 5. **Ingress is stored but never enacted**, exactly as expected: `kubectl get pods -A` shows no Traefik, no ingress-nginx and no AWS Load Balancer Controller pod anywhere in the cluster, `kubectl describe ingress` shows `Address:` blank, and `kubectl get ingress -o jsonpath='{.status}'` returns the empty object `{"loadBalancer":{}}`. 6. **The HPA pipeline worked end-to-end with no fallback needed.** `metrics.k8s.io/v1beta1` and a running `metrics-server` pod were already present on this k3s build before Step 7 — nothing to install. Both transitions were observed live, not inferred.
7. **Exercise 3's assumed "missing `requests.cpu` → permanent `<unknown>`" fault did not hold**, and the reason is worth recording precisely because it is *not* a Floci quirk: the supplied `usms-reports` Deployment sets only `resources.limits` (`cpu: 200m, memory: 128Mi`) with no `requests` block at all, but `kubectl get pod ... -o jsonpath='{.spec.containers[0].resources}'` on the **running pod** showed `"requests":{"cpu":"200m","memory":"128Mi"}` — Kubernetes' own API-server defaulting copies `limits` into `requests` whenever only `limits` is given and no `LimitRange` object says otherwise (confirmed no `LimitRange` exists in `usms`: `kubectl get limitrange -n usms` returned an empty list). The `<unknown>` reading I did see immediately after `apply` was a normal metrics-server cold-start gap (the first scrape window had not elapsed), not evidence of a missing-request fault — it cleared on its own within about 20 seconds. The one fault that genuinely never self-corrected was `minReplicas: 4` equal to `maxReplicas: 4`: `kubectl describe hpa` showed `ScalingLimited: True, Reason: TooFewReplicas`, and the HPA forcibly scaled the Deployment from 2 to 4 pods on its very first reconcile (`SuccessfulRescale: New size: 4; reason: Current number of replicas below Spec.MinReplicas`) and then had no further room to move in either direction regardless of what the metric read. The two one-line fixes applied were `maxReplicas: 4 → 8` (giving it room) and an explicit `requests` block (defensive best practice, since relying on defaulting to mask a missing field is not something I would want in a real manifest even though it worked here).

## Step 17 – ECS + Application Auto Scaling vs Kubernetes + HPA, and ALB vs Ingress

### Scaling comparison

| Question | ECS + Application Auto Scaling (Lab 06) | Kubernetes + HPA (this lab) |
| --- | --- | --- |
| What integer is written? | `desiredCount` on the ECS service | `spec.replicas` on the Deployment |
| Who writes it? | Application Auto Scaling, a separate AWS control plane reacting to a CloudWatch alarm | The HPA controller, a controller running inside `kube-controller-manager`, reacting to the metrics pipeline |
| Where does that thing run? | Outside the cluster entirely — Lab 06's scaling policy and alarms are AWS-managed services with no container of their own | Inside the cluster — the HPA is itself a Kubernetes object, reconciled by a controller that is part of the same control plane as everything else |
| Where does the metric come from? | CloudWatch, fed by the ECS agent's own task-level CPU/memory publishing | `metrics.k8s.io`, fed by `metrics-server` scraping the kubelet's `/stats/summary` on each node |
| What does "50% CPU" mean, 50% of what? | 50% of the task definition's declared CPU units (Lab 06's task-level reservation) | 50% of the Pod's `resources.requests.cpu` (confirmed directly in Exercise 3: the percentage is computed against `requests`, and defaults to `limits` only when `requests` is absent) |
| How is scale-in slowed down? | A cooldown period on the scaling policy (Lab 06's own scale-in cooldown) | `behavior.scaleDown.stabilizationWindowSeconds` (300s here), observed directly taking almost exactly 300 seconds from the last high reading to the actual scale-down event |
| What happens if there is no capacity for the new instance/pod? | Fargate has no fixed capacity to run out of (Lab 04's main selling point); EC2-backed ECS would leave the task `PROVISIONING` | The pod goes `Pending` with `FailedScheduling`, demonstrated directly in Step 11's nodeSelector enforcement test |
| What creates the alarms, if anything? | CloudWatch alarms are first-class objects Lab 06 created explicitly | No alarms exist; the HPA polls the metrics API directly on its own reconcile loop, with no separate alarm object at all |

### Exposure comparison

| Question | ECS + ALB (Lab 05) | Kubernetes + Ingress (Step 16) |
| --- | --- | --- |
| How many AWS objects did I create by hand? | An ALB, a listener, and one target group per service (Lab 05's multi-step build) | Zero new AWS objects on real EKS beyond the one shared ALB the AWS Load Balancer Controller would provision from a single Ingress; on this build, just the one Ingress object itself |
| What is the target type, and why? | Lab 05 registered Fargate ENIs by IP, since Fargate tasks have no instance to register by `instance-id` | `target-type: ip` in this Ingress's own annotation, for the identical reason — pods, like Fargate tasks, have no EC2 instance ID worth registering |
| How are targets registered and deregistered? | Lab 05's target group tracked ENI registrations that ECS itself updated as tasks started and stopped | Kubernetes endpoint objects, continuously reconciled from pod readiness — confirmed in this lab's own `describe ingress` output, which shows live pod IPs under each path's "Backends" with no registration step of my own |
| How are competing routing rules disambiguated? | Lab 05 used explicit numeric listener-rule priority | Longest matching path prefix wins, not declaration order — a materially different disambiguation rule from Lab 05's explicit priority field |
| What would I change to move this to another cloud? | Nearly everything: the ALB, listener and target groups are AWS-specific objects with no portable equivalent | Only the controller and its annotations (the `alb.ingress.kubernetes.io/*` keys); the Ingress's `rules`/`paths`/`backend` structure is the same on any conformant cluster |
| What is the cost of exposing ten services? | Ten target groups behind the one ALB Lab 05 already pays for — marginal cost per service is a target group, not a new load balancer | One Ingress object with ten path rules behind the one ALB the controller provisions — on real AWS this is the entire point of Exercise 4's "do not add a second LoadBalancer" constraint: paths are free, load balancers are not |

### What each arrangement does during a bad afternoon for the AWS control plane, and which is easier to debug

If the AWS control plane itself degrades, Application Auto Scaling cannot write a new `desiredCount` at all — it is an AWS API call, full stop, and Lab 06's own scaling history would simply go quiet with no local fallback. The HPA, by contrast, is a controller running **inside** the cluster's own control plane; as long as `kube-apiserver` and `metrics-server` are reachable (and on EKS, `kube-apiserver` is itself AWS-managed, so a true AWS-wide outage would still affect it) it keeps reconciling with no dependency on CloudWatch or any other regional AWS service. Debugging is correspondingly easier on the Kubernetes side for a working engineer: `kubectl describe hpa` surfaces `Conditions`, `Events` and the exact metric value in one command, all inside the same API the rest of the cluster uses, whereas diagnosing a stalled ECS scaling policy means correlating a CloudWatch alarm's state, the scaling policy's own cooldown, and the ECS service's event log across three separate AWS consoles or API calls.

### Which I would choose for USMS, and the strongest counter-argument

For USMS I would still choose **ECS with Application Auto Scaling**, the same conclusion Lab 07's notes reached for the platform choice generally: USMS's traffic shape (quiet for eight months, sharp for two) is exactly the case Lab 06 already solved cleanly, and this lab's own node-group-scaling step (Step 10) failing outright on this build is a vivid illustration of the operational floor EKS adds — on real AWS that floor is the Cluster Autoscaler or Karpenter, a second scaling system the HPA alone does not replace, where ECS/Fargate needs nothing of the kind. The strongest argument against that choice: the HPA's `behavior` block (independent scale-up and scale-down policies, multiple weighted policies, a precise stabilization window) is strictly more expressive than Application Auto Scaling's single target-tracking policy, verified directly in this lab when the scale-down event landed within seconds of the exact 300-second window configured — if USMS ever needed scaling logic finer than "add capacity above X%, remove it after Y minutes," Kubernetes' richer primitive would be the one already capable of expressing it.

## Exercise 5 Part 3 — ECS or Kubernetes for USMS

Having now run both an ECS-based scaling system (Lab 06's Application Auto Scaling) and a Kubernetes-based one (this lab's HPA) against the same application, I still recommend **ECS with Fargate and Application Auto Scaling** for USMS. Three specific observations from these two practicals support it. First, Lab 06's entire scaling story needed one scaling policy and two CloudWatch alarms; this lab needed an HPA object, a metrics pipeline that happened to already be installed (Step 7 would have been a fourth object if it were not), and — on real AWS — a Cluster Autoscaler or Karpenter to actually grow the node group the HPA's extra pods need to land on, a layer ECS/Fargate has no equivalent of at all. Second, Step 10 of this lab failed outright on this build with `UnknownOperationException`, a direct, observed illustration of the extra moving part EKS adds at the infrastructure layer that ECS simply does not have: Fargate has no node group to scale in the first place. Third, the Ingress-vs-ALB comparison in Step 17 showed that once a workload is actually exposed, the two platforms converge almost completely — `target-type: ip`, path-based routing, and the cost model of one shared load balancer are identical in spirit, which means the portability Kubernetes buys is paid for almost entirely in day-one setup complexity and ongoing node-level operations, not in the request-serving path itself. The strongest argument against this recommendation, and the one I take most seriously: USMS's quiet months are exactly when a small platform team has time to absorb Kubernetes' extra operational surface, and if USMS ever needs a capability ECS genuinely cannot express — a PodDisruptionBudget's hard guarantee during a voluntary disruption (Lab 07 Exercise 4), or the HPA's independently-tunable scale-up/scale-down behavior demonstrated in this lab — the cost of migrating later, after USMS's own object model has grown ECS-specific for years, would be far higher than adopting Kubernetes now while the application is still small enough that `manifests/lab-07/` and `manifests/lab-08/` together are the entire deployment.

## Review Questions (Section 14)

**1. A colleague says an HPA with `averageUtilization: 50` "scales when the node hits 50% CPU". Correct them. What happens if the container's CPU request is halved without changing the HPA, and does the workload end up with more or less capacity?**  
**Answer:**
They are wrong about the denominator: the HPA's percentage is computed against the **container's own `resources.requests.cpu`**, never against the node's total capacity — confirmed directly in this lab's Step 6, where `kubectl describe node`'s "Allocated resources" table and the HPA's own `TARGETS` column are two completely separate numbers computed from different inputs. A node running at 90% overall utilization from other workloads has no effect on this HPA at all if `usms-enrolment`'s own pods are individually using 10% of their 50m request; conversely, the HPA could trigger a scale-out while the node itself sits nearly idle, exactly the asymmetry Exercise 3 exposed when `usms-reports`'s `TARGETS` column tracked the pod's own request, not node pressure. If the CPU request were halved (50m → 25m) without touching the HPA's `averageUtilization: 50` target, the **same absolute CPU usage now reads as a higher percentage** (usage ÷ a smaller request = a bigger fraction), so the HPA would scale out sooner and to a higher replica count for identical real traffic — the workload ends up with **more capacity**, not less, because the controller is chasing a percentage of a shrunken denominator and over-provisions replicas relative to what the traffic actually needs.

**2. `usms-enrolment` must handle ten times its traffic by a deadline. Give an ordered scaling plan using the four scaling dimensions, with a check after each step, and name the one dimension that cannot change in place.**  
**Answer:** In order: (1) **Vertical, workload** — raise `resources.requests.cpu`/`limits.cpu` only if profiling shows the container itself is CPU-starved per request, checked with `kubectl top pods` against the existing 50m/200m baseline from Step 6; (2) **Horizontal, workload** — raise the HPA's `maxReplicas` (this lab's enrolment HPA caps at 8, deliberately low for a demo), checked with `kubectl get hpa` confirming the new ceiling is accepted; (3) **Horizontal, nodes** — grow the node group's `desiredSize`/`maxSize` so there is somewhere for the extra pods to land, checked with `kubectl get nodes` for a rising `Ready` count (this is precisely the step that fails on this Floci build, per Finding 1 above, which is itself the honest answer for why this step needs to be checked rather than assumed); (4) **Vertical, nodes** — only if step 3's larger node count still cannot fit the workload's per-pod footprint, move to a larger EC2 instance type via a new node group, checked by confirming the new instance type's allocatable capacity with `kubectl describe node`. The one dimension that **cannot change in place**: a node group's `instanceTypes` field is immutable after creation (this lab's own `usms-eks-nodes` was created with `t3.small` and `describe-nodegroup` has no `update-nodegroup-config` parameter for instance type at all) — vertical node scaling on EKS always means creating a new node group and migrating workloads onto it, never resizing the existing one.

**3. Lab 6's Application Auto Scaling and this lab's HPA both write one integer. Give two consequences of one running outside the workload's cluster and the other inside it, at least one concerning failure.**  
**Answer:** First, a non-failure consequence: because the HPA runs inside the same API server as everything else it scales, `kubectl describe hpa` can show the *exact* reasoning (the `Conditions` and `Events` fields observed directly in this lab — `ValidMetricFound`, `TooFewReplicas`, `SuccessfulRescale` with its precise message) in the same tool and the same authentication context as every other object, while Application Auto Scaling's reasoning lives in a separate AWS service (CloudWatch alarms, scaling activities) that Lab 06 had to query with entirely different commands. Second, the failure consequence: if the cluster's own control plane degrades — `kube-apiserver` unreachable, or `metrics-server` crashed — the HPA controller that depends on that same control plane degrades with it, and has no way to keep scaling "from outside" the way Application Auto Scaling would continue operating even if a single ECS service's tasks were unhealthy, since Application Auto Scaling's own control loop lives entirely outside the thing it scales. In other words, the HPA's integration is a double-edged sword: better observability through shared tooling, but a shared fate with the exact system whose degradation would most need a working autoscaler.

**4. The HPA raises `replicas` from 4 to 8 and four pods sit `Pending` for twenty minutes. Explain this using the two-control-loops picture, name the component that would normally resolve it, and say why lowering the CPU request is a bad fix.**  
**Answer:** This is the HPA's control loop (workload-level: "how many pods should exist") correctly doing its job while a second, independent control loop (node-level: "is there anywhere to put them") has nothing to offer — exactly the split this lab's own Step 10/11 distinction draws between workload autoscaling and data-plane autoscaling, and directly observed in Step 11's enforcement test, where an unsatisfiable `nodeSelector` left pods `Pending` with `FailedScheduling` indefinitely, with the Deployment's own replica count never in question. The component that would normally resolve it on real AWS is the **Cluster Autoscaler** (or Karpenter): it watches for exactly this symptom — pods `Pending` due to insufficient capacity, not a bad selector — and requests new nodes from the ASG/node group to make room, closing the loop the HPA alone cannot close. Lowering the CPU request is a bad fix because it does not add capacity, it only **lies about how much is needed**: per Review Question 1's own arithmetic, a smaller request makes the same absolute CPU usage read as a higher percentage, which could even trigger the HPA to ask for *more* replicas, each believing it needs less room than it actually uses — worsening, not fixing, a problem that was never about the request's accuracy in the first place.

**5. Students conflate NodePort with LoadBalancer, and Service with Ingress. Take one pair, explain the distinction, and give a requirement that the wrong choice fails and the right one meets.**  
**Answer (Service vs Ingress):** A Service is a **Layer-4** construct — one stable virtual IP and port, with no concept of an HTTP path or hostname at all; an Ingress is a **Layer-7** construct — a set of HTTP routing rules (path, host) that still needs a Service as its ultimate target, confirmed directly in this lab's own Step 16, where `usms-portal-ingress`'s three path rules each name a Service (`usms-enrolment`, `usms-results`, `usms-gateway`) rather than a pod. The requirement the wrong choice fails: "expose `/enrolment`, `/results` and `/` on USMS's single public hostname without paying for three separate load balancers" (Exercise 4's exact constraint) — a bare Service per backend would need either three separate `LoadBalancer` Services (three ALBs, three bills) or hand-rolled proxying (exactly what Lab 07's `usms-gateway` already did at the application layer, before Kubernetes' own Ingress existed in this course). A single Ingress meets the requirement directly: one object, three path rules, one ALB — demonstrated in this lab by the one Ingress correctly resolving all three paths to the right Service's live endpoints in a single `describe ingress` call.

**6. Step 16's Ingress sends `/enrolment` straight to `usms-enrolment`, bypassing `usms-gateway`. Argue for one route, say what you would delete, and address what the gateway does that the Ingress rule does not.**  
**Answer:** I would argue for **keeping the Ingress's direct route and deleting `usms-gateway`'s own `/enrolment/` proxy rule**, not the reverse. The gateway's nginx `proxy_pass` to `usms-enrolment.usms.svc.cluster.local` does exactly one thing the Ingress's direct path-to-Service rule cannot: it is a single, named, scriptable place to add cross-cutting logic (this lab's gateway also adds `X-Forwarded-For` and sets `Host` on every proxied request) without touching the Ingress at all — a legitimate reason to keep an application-level gateway in general. But for USMS specifically, that logic is thin enough (two header rewrites) that the Ingress controller's own equivalent annotations could carry it, and running the request through two reverse proxies in series (the ALB/Ingress, then nginx, then finally the pod) for no additional behavior is pure latency and one more thing that can fail — confirmed structurally in this lab, since `kubectl describe ingress` showed `/enrolment` resolving to `usms-enrolment`'s live endpoints with no dependency on `usms-gateway` being healthy at all. What I would delete: the gateway's `/enrolment/` and `/results/` location blocks (collapsing to just `/timetable/` and `/`, its own identity endpoint), while keeping the Ingress's three-path routing as the single source of truth for which hostname path reaches which backend.

**7. A PodDisruptionBudget with `minAvailable: 1` did not stop `kubectl delete pod`. Why is that correct? Distinguish voluntary from involuntary disruption and give one realistic scenario where the PDB saves a production service.**  
**Answer:** This is correct because a PDB only governs the **Eviction API** (`/pods/{name}/eviction`), the specific endpoint `kubectl drain` and a cluster-autoscaler node replacement use — it was never designed to intercept a direct object deletion, confirmed exactly in this lab's Step 12: `kubectl create --raw ".../eviction"` against `usms-gateway-b564df77f-d9nnj` returned `Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget`, while `kubectl delete pod` on the very same pod a moment later succeeded instantly with no PDB involvement at all. **Voluntary disruptions** are operator- or controller-initiated actions that go through the Eviction API and therefore respect a PDB — a node drain, a cluster-autoscaler scale-down, a rolling node replacement. **Involuntary disruptions** are everything a PDB was never meant to stop — a node crashing, a pod OOM-killed by the kubelet, or (the case tested here) a human directly deleting the object, which the API server honors unconditionally because `delete` is not `evict`. A realistic scenario where the PDB genuinely saves a production service: an operator runs `kubectl drain` to patch a node's OS, and the PDB's `minAvailable: 1` correctly blocks the eviction of the last healthy replica of a single-node-pinned service mid-drain — exactly what Lab 07 Exercise 4 demonstrated directly, with the drain command itself stalling and retrying rather than taking the service to zero.
